1. INTRODUCTION                                          *codeview-introduction*
                                                                    *codeview*

codeview shows the changes of a commit, or of a range of commits. You browse
the changed files in a sidebar, read the diffs inline or side by side, and
write comments on the lines. You export the comments as markdown, and you send
them to a GitHub pull request.

The plugin works on a git repository and on a jj repository, through one
backend interface. It writes no file of your repository: the comments of a
review live in one markdown file of their own. See |codeview-comments-store|.

Version 0.1.0. Start here: >vim

    :Codeview HEAD~3..HEAD
<
Then press <CR> on a file of the sidebar. |codeview-keymaps| holds every key.

==============================================================================
2. REQUIREMENTS                                          *codeview-requirements*

- Neovim 0.11 or later.
- git, for the git backend.
- jj 0.45 or later, for the jj backend (optional).
- gh, for GitHub pull request review (optional).

A tool that is not in $PATH needs an option with its path. See
|codeview-binaries|.

==============================================================================
3. SETUP                                                        *codeview-setup*

The plugin works without a setup call. Every option then holds its default
value.

To change an option, call setup(): >lua

    require("codeview").setup({
      diff = { style = "split" },
    })
<
                                                          *codeview.setup()*
codeview.setup({opts})
    Merge {opts} into the defaults, validate the result, and store it.

    Return: ~
        The active configuration, or nil and a message when {opts} is invalid.

                                                          *codeview.config()*
codeview.config()
    Return the active configuration table.

                                                                  *g:codeview*
You can also set the variable `vim.g.codeview` before the plugin loads. The
plugin then calls setup() with that table: >lua

    vim.g.codeview = { sidebar = { position = "right" } }
<

4. COMMANDS                                                  *codeview-commands*

                                                                   *:Codeview*
:Codeview {rev}
    Review one commit. The base of the review is the parent of {rev}. For the
    first commit of the repository the base is the empty state.

    The command sends the argument to the backend as it is. A revision
    argument can hold spaces, for example `main@{2 days ago}`.

    Examples: >vim

        :Codeview HEAD
        :Codeview HEAD~3..HEAD
        :Codeview main...feature
<
:Codeview {rev}..{rev}
    Review the changes between the two revisions. The left side is the base.
    It is not part of the review.

:Codeview {rev}...{rev}
    Review the changes since the merge base of the two revisions.

:Codeview {revset}                                        *codeview-revsets*
    On a jj repository the argument is a revset. The command sends the text to
    jj as it is. The head of the revset is the new side of the review. The
    parent of the roots of the revset is the base.

    A revset that names more than one head is an error. Select one head.

    Examples: >vim

        :Codeview @
        :Codeview ::@
        :Codeview trunk()..@
<
                                                                *:Codeview-pr*
:Codeview pr [{number}]
    Review the GitHub pull request {number}. Without {number} the command
    takes the pull request of the current branch. The command needs the gh
    CLI. See |codeview-github|.

    Examples: >vim

        :Codeview pr 128
        :Codeview pr
<
:Codeview
    Open the commit picker. Select one commit to review it.

:Codeview!
    Open the picker in the range mode. Select the first commit of the range,
    then the last commit. Both commits are part of the review. The second list
    holds only the descendants of the first commit.

                                                        *codeview-subcommands*
The first word of the argument can also name a subcommand. A subcommand name
wins over a revision of the same name. To review a revision that a subcommand
names, write the revision as a range, for example `:Codeview close^..close`.

                                                             *:Codeview-close*
:Codeview close
    Close the review session. The command closes the windows and the buffers
    of the session.

                                                            *:Codeview-reopen*
:Codeview reopen
    Open the session that closed last again. The command opens the same range
    or pull request, then the same file on the same line, in the same diff
    style. The sidebar and the overview open or close as they were, and the
    sidebar gets its expanded directories again. The plugin keeps the record
    in memory only, so it does not survive a restart of Neovim. Without a
    closed session, or while a session runs, the command gives a warning.
    See |codeview.reopen()| and |codeview-close-confirm|.

                                                              *:Codeview-back*
:Codeview back
    Go back to the review from a file of the working copy. The window takes
    the diff of the file again, with the cursor on the row of the line that
    the file holds. A review of the working-copy commit reads its data again
    first. See |codeview-edit-back| and |codeview-edit-reload|.

                                                           *:Codeview-refresh*
:Codeview refresh
    Read the review again from the repository. The command resolves the range
    of the review again, so a new commit, an amend, or a rebase reaches the
    review. On jj it writes the working copy into `@` first. See
    |codeview-refresh|.

                                                             *:Codeview-files*
:Codeview files
    Open the changed-files sidebar and put the cursor in it. The command
    closes the sidebar when the sidebar is open.

                                                          *:Codeview-comments*
:Codeview comments
    Open the comment overview and put the cursor in it. The command closes the
    overview when the overview is open. See |codeview-overview|.

                                                            *:Codeview-export*
:Codeview export [{register}]
    Render the comments of the session as markdown. The text goes into a
    scratch buffer and into the register of the `export.register` option.
    {register} replaces the option for this call, for example
    `:Codeview export z`. See |codeview-export|.

:Codeview! export [{register}]
    Write the register only. The command opens no scratch buffer.

                                                            *:Codeview-submit*
:Codeview submit [{event}]
    Send the comments of the session to the pull request, as one review. The
    command shows a summary and posts only after you confirm it. {event} is
    `comment`, `approve`, or `request-changes`. Without {event} the command
    asks for it. See |codeview-submit|.

:Codeview! submit [{event}]
    Post with the default text of the review. The command asks no question
    about the text.

                                                               *codeview-quit*
Neovim quits when a review that the command line of Neovim started ends: >sh

    nvim -c "Codeview pr 128"
    nvim +"Codeview HEAD"
<
The review ends when you close the session, or when you close the picker
without a pick. For a pull request that does not open, the loading view shows
the error, and `q` quits Neovim. After another error, Neovim stays open, so
that you can read the message.

A second `:Codeview` in the same Neovim replaces the review. Neovim quits
after the last review only. A buffer with changes stops the quit.

The `quit` option sets the default. "startup" quits after a review from the
command line, and "never" keeps Neovim open. A flag in the argument replaces
the option for one call:

++quit      Quit Neovim when the review ends, also after a command that you
            type in Neovim.
++noquit    Keep Neovim open when the review ends. The flag also stops the
            quit of the review that runs.

A flag can stand anywhere in the argument. A subcommand takes no flag.
Examples: >vim

    :Codeview ++quit pr 128
    :Codeview HEAD ++noquit
<

5. SESSIONS                                                  *codeview-sessions*

A session holds the backend handle, the resolved range, the commits of the
range, and the files that the range changes. The plugin keeps one session. A
second open closes the session that runs. A failed open keeps it.

The session sends these events: >

    User CodeViewSessionOpened      a session opened
    User CodeViewSessionRefreshed   a session read its data again
    User CodeViewSessionClosed      a session closed
<
The `data` field of the event holds plain values only: >

    data.id         number of the session
    data.spec       text that names the range
    data.files      number of changed files
    data.commits    number of commits in the range
<
Neovim copies the payload of a User event, so the payload cannot hold the
session object. To use the session methods, read the session with
|codeview.session()|: >lua

    vim.api.nvim_create_autocmd("User", {
      pattern = "CodeViewSessionOpened",
      callback = function(event)
        print(event.data.spec, require("codeview").session():summary())
      end,
    })
<
The close event comes after the session ended. |codeview.session()| gives nil
in that handler.

A session reads its data again with `session:refresh()`. On a review of the
working-copy commit, `session:reload()` also takes the new state of the
working copy. The diff view and the sidebar make that call for you. See
|codeview-edit-reload|.

                                                     *codeview-commit-message*
The commits of the range come before the files. Every commit is one entry of
the sidebar, under a group node, and its name holds the short id and the
subject of the commit. The newest commit reads first, and the oldest commit
is at the bottom, as in the log of jj or git. The document of a pull request
lists its commits in the same order.

An entry opens like a file. The document of a commit holds:

    - the id, the author, and the date,
    - the message, with the subject and the body,
    - the files that the commit changes, with their status marks.

Comment on the document like on a line of code. The comment takes the commit
of the document, so every comment stays with its own commit.

The message is markdown text, and so is the description of a pull request.
The buffer of a commit document and of the pull request document therefore
has the `markdown` filetype, and the message has no indent. The markdown
tools of your configuration then work on the document: the treesitter
highlighter of Neovim, and a render plugin like render-markdown.nvim or
markview.nvim. The buffer stays read-only, and the keys of codeview stay.

The header lines are plain text. The file list and the commit list keep an
indent of four spaces, so markdown shows them as a code block. The buffer
shows no diagnostics, because a linter of markdown reports on the header and
on the lists that codeview writes. Set `diff.syntax` to false to keep the
filetype of a diff. See |codeview-diff-syntax|.

A document is no file of the repository, and it has one side, so it stays in
the inline style. GitHub takes no comment on a commit message, so
|:Codeview-submit| keeps such a comment local and reports it in the summary.

Set `commit_message` to false to leave the commits out: >lua

    require("codeview").setup({ commit_message = false })
<

6. SIDEBAR                                                    *codeview-sidebar*

The sidebar shows the files that the range of the session changes, as a tree.
|:Codeview| opens it with the session, at the side that `sidebar.position`
names. Set `sidebar.auto_open` to false to open the sidebar with
|:Codeview-files| only. A session that starts from |codeview.open()| opens no
panel.

The first two lines are the header. The first line holds the range. The
second line holds the number of files and the number of commits. The tree
comes after an empty line: >

    9b2688a5..ec056be0
    4 files, 2 commits

      ▾ dir
      │   renamed.txt ← nested.txt R
    ▸   a.txt M
        added.txt A
        keep.txt D
<
The tree holds one node per directory and one node per file. A chain of
directories with one child each becomes one node, for example
`lua/codeview/vcs`. Directories come before files, and both come in
alphabetical order.

Each file line ends with a status mark: >

    A    the range adds the file
    M    the range changes the file
    D    the range deletes the file
    R    the range renames the file
    C    the range copies the file
    T    the range changes the type of the file
    U    the file is unmerged
    ?    the backend gave another status
<
A rename line and a copy line also show the old path, after an arrow. A
directory that hides its children shows the marks of the files below it.

The marker "▸" and the highlight group |hl-CodeViewCurrent| mark the file that
the diff view shows. The marker moves with every file that you open. A
directory that hides the marked file opens again.

                                                     *codeview-sidebar-keymaps*
The sidebar buffer holds these maps. |codeview-config| names the keys: >

    <CR>        open the file under the cursor, or toggle a directory
    <Tab>       toggle the directory of the line under the cursor
    zR          show the children of every directory
    zM          hide the children of every directory
    ]f          open the next file
    [f          open the previous file
    <leader>ct  switch the diff style
    <leader>co  open or close the comment overview
    <leader>cR  read the review again from the repository
    q           close the review session
<
The next-file key and the previous-file key follow the order of the tree.
They step over the directory nodes, and they also reach a file in a directory
that hides its children.

The buffer of the diff view holds the maps `]f`, `[f`, and `q`. You walk
through the files without a move back to the sidebar. Each key press moves one
file, also while the backend still reads the file of the last press.

                                                       *codeview-sidebar-icons*
The tree uses text icons from `sidebar.icons`. The plugin needs no icon font
and no devicons plugin. For a terminal without support for the default
icons, set plain characters: >lua

    require("codeview").setup({
      sidebar = {
        icons = {
          expanded = "-",
          collapsed = "+",
          file = " ",
          guide = "|",
          current = ">",
        },
      },
    })
<

                                                            *codeview-layout*
The sidebar keeps its width. A file that opens takes the window of the file
that was open, so the tab page holds the same windows before and after. Only a
resize by hand changes the width of a panel, and a later open keeps that
width.

Neovim makes the windows of a tab page equal again after every open and every
close, when 'equalalways' is on. codeview holds that option off while it opens
or closes its own windows, and puts the width of every panel back afterwards.
Your own windows keep their behavior.

                                                   *codeview-sidebar-comments*
The first line of the sidebar is "Comments", with the number of comments of
the review. `<CR>` on that line opens the comment overview, and closes it
again. See |codeview-overview|.

                                                      *codeview-sidebar-mouse*
A double click acts like `<CR>`: it opens the file under the pointer, folds
the directory under the pointer, or opens the comment overview. The key comes
from the `open_file` option, so a list without `<2-LeftMouse>` takes the mouse
out. The 'mouse' option must hold the mode, which it does by default.

7. DIFF VIEW                                                     *codeview-diff*

The diff view shows one changed file in the main window. It reads both sides
of the file from the backend and compares them with |vim.diff()|. Two styles
show the result of that comparison:

    inline    one unified diff in one buffer
    split     two aligned buffers, the old side left, the new side right

The `diff.style` option names the style of the first file. |codeview-diff-style|
describes the switch between the two styles.

The buffers are read-only. Their filetype is `codeview-diff`. A commit
document, the pull request document, and a pr-agent document have the
`markdown` filetype. See |codeview-commit-message|. The buffer variable `b:codeview_filetype` holds
the filetype of the file itself: >

    @@ -1,6 +1,6 @@
     line 01
     line 02
    -line 03
    +line 03 changed
     line 04
     line 05
     line 06
    ⋯ 20 unchanged lines
    @@ -27,7 +27,7 @@
     line 27
<
In the inline style the first character of a line is the marker. A space marks
an unchanged line, `-` marks a removed line, and `+` marks an added line. The
status column shows the line number of the old file and the line number of the
new file.

A line that only one side holds shows one number. The plugin highlights a
removed line with |hl-CodeViewDiffDelete| and an added line with
|hl-CodeViewDiffAdd|. With `diff.word_diff` the changed part of a line also
gets |hl-CodeViewDiffTextDelete| on the removed line and
|hl-CodeViewDiffTextAdd| on the added line. The diff pairs a removed line
with the added line that looks most like it, so a renumbered list shows only
the changed numbers. A line without a similar partner keeps a plain row.

                                                         *codeview-diff-syntax*
The diff keeps the colors of the code. A diff buffer holds two revisions with
a marker in front, so treesitter cannot attach to it. codeview parses each
side as a whole file instead, and writes the captures of the highlights query
into the rows of that side.

The diff colors then stay in the background: |hl-CodeViewDiffAdd| and
|hl-CodeViewDiffDelete| take the background of `DiffAdd` and `DiffDelete` and
carry no foreground, so the code keeps the colors of its language. The word
marks paint over the row, so the changed part of a line shows in the stronger
color of its side.

The word groups take the background of the row with a quarter of the color of
`Added` or `Removed` on top, so a changed word shows in the color of its side.

The layer needs a treesitter parser for the language of the file. A file
without one keeps the plain diff colors, and so does a binary file or a diff
above a size limit. A side of more than 1 MB gets no parse, because the parse
blocks the editor. A line of more than 10000 bytes keeps the plain diff
colors, and the lines after it keep the colors of their language.

A document gets no colors from this layer: a commit, the pull request, or a
pr-agent result. Its buffer has the `markdown` filetype, so the markdown
tools of your configuration color it. See |codeview-commit-message|.

Set `diff.syntax` to false to turn the layer off. The row colors then take
their foreground again. A document then keeps the `codeview-diff` filetype,
and shows plain: >lua

    require("codeview").setup({ diff = { syntax = false } })
<
                                                        *codeview-diff-context*
The view shows `diff.context` unchanged lines around each hunk. It hides a
longer unchanged section behind one filler row: >

    ⋯ 20 unchanged lines
<
A section that hides fewer than two lines stays open, because the filler row
costs as many screen rows as the lines that it hides.

The view reads `diff.context` at every render. A setup() call with a new value
therefore changes the next render, also of the file that is open.

Put the cursor on the row and press `za` to show the hidden lines. A second
press hides them again. `zR` shows every hidden line of the file, and `zM`
hides them all again. The hunk header keeps the line numbers of the collapsed
form, because the header names the position of the hunk in the file.

A file without a text diff shows one note instead of a diff: >

    The file has no changes.    a rename or a copy without a content change
    The file is empty.          both sides hold no line
    The file is binary. It has no text diff.
    The file changes only its line endings (CRLF and LF).
<
The last note stands for a change of CRLF to LF, or of LF to CRLF, and no
other change. Such a change touches every line, so a diff of every line says
less than the note.

                                                            *codeview-diff-eol*
A side that does not end with a line break gets one more row after its last
line, like the diff of git: >

    \ No newline at end of file
<
The row holds no line of the file, so a comment cannot anchor to it. A change
that only adds or removes the last line break shows the last line as removed
and added, with the row on the side without the break.
                                                          *codeview-diff-limit*
The view reads the file of one row of the sidebar, and no other file. A range
of 400 files therefore opens as fast as a range of four.

A file can still be too large to compare. Two options limit the size:

    `diff.max_lines`   highest number of lines of the two sides together
    `diff.max_bytes`   highest number of bytes of the two sides together

The byte limit stops a file with few but very long lines, for example a
generated file. Above a limit the view compares nothing and shows two rows: >

    The diff holds 48210 lines. The limit diff.max_lines is 20000.
    Press <CR> to show it.
<
The note of the byte limit reads the same way: >

    The diff holds 3145728 bytes. The limit diff.max_bytes is 2000000.
    Press <CR> to show it.
<
The `load_diff` key reads the file again, without both limits. The key maps on
such a diff only, so `<CR>` keeps its own action in every other diff. The
limits apply to one file at a time, and the next file opens as usual. Set an
option to 0 to remove its limit for every file. The defaults are 20000 lines
and 2000000 bytes.

|:Codeview-submit| never sees the limit. It maps the position of a comment on
the full diff of the file, whether the view rendered that diff or not.

                                                          *codeview-diff-split*
The side-by-side style shows the old version at the left and the new version
at the right: >

    @@ -1,4 @@              @@ +1,6 @@
    one                     one
    two                     two changed
    three                   three
    four                    four
                            five
                            six
<
Both sides hold the same number of rows, so a change sits on the same screen
row in both windows. A change that adds more lines than it removes gets a
filler row at the left, and a change that removes more lines than it adds gets
a filler row at the right. A filler row holds no text. It shows the highlight
|hl-CodeViewDiffFiller| and virtual text, so it never reads as a line of the
file.

The two windows scroll and move the cursor together, through 'scrollbind' and
'cursorbind'. The mouse wheel scrolls both windows too, also when the pointer
sits over the window without the focus. The status column of the left window
shows the line numbers of the old file, and the status column of the right
window the numbers of the new file. Both styles hide the same unchanged
sections, and `za`, `zR`, and `zM` work in both.

The two windows show one diff together. If you close one of them, the view
takes the inline style in the window that stays. The style of the next file
stays side by side, so the next file opens side by side again.

                                                          *codeview-diff-style*
Press `<leader>ct` in the diff view or in the sidebar to switch the style. The
switch keeps the diff, so the backend reads no file again, and it keeps the
cursor on the same line of the file. A cursor on a removed line moves to the
left window. A cursor on a hunk header, or on the row of a collapsed section,
stays on that header or on that row. The new style also becomes the style of
the next file, so the next file opens in the same style. The `diff.style`
option keeps its value. A later setup() call sets the style of the next file
back to the option.

To start every review in the side-by-side style, set the option: >lua

    require("codeview").setup({ diff = { style = "split" } })
<
                                                        *codeview-diff-keymaps*
The diff buffer holds these maps. |codeview-config| names the keys: >

    ]h          jump to the next hunk
    [h          jump to the previous hunk
    za          show or hide the section under the cursor
    zR          show every hidden line
    zM          hide every section again
    ]f          open the next file
    [f          open the previous file
    <CR>        render a diff above a size limit, on such a diff
    <leader>ct  switch the diff style
    i a o O     comment on the line under the cursor
    I A c       comment on the selected lines, in the visual mode
    <leader>cc  comment on the line or on the selection
    <leader>ce  edit the comment under the cursor
    <leader>cd  delete the comment under the cursor
    <leader>cr  resolve the comment, or open it again
    <leader>co  open or close the comment overview
    <leader>cR  read the review again from the repository
    K           show the comment under the cursor in a float
    q           close the review session
<
|codeview-keymaps| holds the full list, with the option name of each key.

The diff view sends one event: >

    User CodeViewFileOpened    a file opened in the view
<
The `data` field of the event holds these values: >

    data.session    number of the session
    data.index      position of the file in the file list
    data.path       path of the file
    data.status     status of the file in the range
    data.style      style of the render, "inline" or "split"
    data.buf        buffer that holds the diff
<
The event also comes after a change of the style, because the buffer of the
file is a new buffer then.

                                                        *codeview-diff-linemap*
The view keeps a line map. The map holds one record per buffer row, with the
kind of the row, the line in the old file, the line in the new file, and the
hunk of the row. Read the map with |codeview.view()|: >lua

    local map = require("codeview").view().map
    local row = vim.api.nvim_win_get_cursor(0)[1]
    print(map:kind(row), map:file_line(row))   -- "add", 12, "new"
    print(map:buf_row(12, "new"))              -- 5
<
                                                              *codeview-edit*
`gf` leaves the review and edits the real file. The window of the diff takes
the file of the working copy, with the cursor on the line that the diff shows.
The buffer is a normal file buffer, so `:w` writes it.

The working copy is not the revision of the review. The line is therefore the
line of the change, and the text around it can differ. A row of the old side
has no line of its own, so the nearest row of the new side answers for it.

The sidebar stays open, and `<CR>` on the file reads its diff again. The
window of the file leaves the session, so |:Codeview-close| keeps it open.

The key also works on a file line of the sidebar. It reports a commit document
and a file that the working copy does not hold, for example a file that the
range deletes.

                                                         *codeview-edit-back*
`<leader>cb` goes back. The window takes the diff of the file again, with the
cursor on the row of the line that you left. |:Codeview-back| does the same
from any window.

The key sits on the file that the edit key opened, and on no other buffer. It
is the way back, because the jump list of Neovim holds no entry for the diff:
the diff buffer wipes itself when the window leaves it.

A file with changes that are not written needs 'hidden', or a write first,
because the window cannot leave a modified buffer otherwise.

                                                        *codeview-edit-reload*
The file that you write is a file of the working copy. On jj the working copy
is the commit `@`. A review of `@` therefore holds old content after your
write.

The way back reads the review again for you. If the head of the range is the
commit of the working copy, codeview writes the working copy into that commit.
The new commit id becomes the head of the range. codeview then reads the files
and the commits of the range again, and the sidebar and the comment overview
show the new list.

The open key of the sidebar reads the review again in the same way, so the
other way back into the review also holds your writes. A file that leaves the
range gets a message, because the review has no diff to show for it.

git holds the working copy outside the commits, so a write moves no commit
there. A git review therefore keeps its data.

Set `auto_reload` to false to keep the data of the review as-is: >lua

    require("codeview").setup({ auto_reload = false })
<
                                                            *codeview-refresh*
The reload takes the working copy only. It never moves the base of the range,
and it never adds a commit to the review. `<leader>cR` does that: it reads the
whole review again from the repository.

The key resolves the text of the range again. `trunk()..@` and `HEAD~3..HEAD`
therefore follow the new commits, so a `jj new`, a `git commit`, an amend, or
a rebase reaches the review. On jj the key writes the working copy into `@`
first, like the reload. A review of a pull request holds two resolved commits,
so it reads the same two commits again.

The key works in the sidebar, in the diff view, and in the comment overview.
The open file stays open, with the cursor on the same line of the file. A file
that leaves the range gets a message, and its window closes.

`:Codeview refresh` and `require("codeview").refresh()` do the same from any
window.

The refresh key, `:Codeview refresh`, the back key, `:Codeview back`, and
`<CR>` in the sidebar run without a block. The editor stays usable while the
backend reads the repository, and the views show the new state when the read
ends. `require("codeview").refresh()` blocks, and returns after the read.

                                                       *codeview-auto-refresh*
An open review also follows the repository by itself. codeview watches the
state directories of the repository: `.jj/repo/op_heads/heads` on jj, and the
git directory with `refs/heads` on git. Every operation writes there.

After such a write, codeview resolves the range of the review again, without
a block of the editor. New
commit ids mean that the range moved, so the plugin reads the files and the
commits again. In a colocated jj repository the check first imports the git
refs with `jj git import`, so a `git commit` reaches the review too. The sidebar, the comment overview, and the open diff show the
new state. Equal ids mean that the review is current, and nothing happens.

So a `jj new`, a `jj describe`, a `git commit`, an amend, or a rebase in
another terminal reaches the review within a second. The check reads the
repository only. It never writes the working copy into a commit, because the
working copy belongs to you. The refresh key takes the working copy with it.
See |codeview-refresh|.

A failed check keeps the data of the review and gives one message. The next
checks stay quiet until a check succeeds.

Set `auto_refresh` to false to stop the watcher: >lua

    require("codeview").setup({ auto_refresh = false })
<
The refresh key and `:Codeview refresh` still work then.

8. COMMENTS                                                  *codeview-comments*

A comment holds a file, a line range, a side of the diff, a commit, and a
markdown body. The plugin keeps every comment of a session in one file. A
reopen of the same range shows the comments again.

The diff buffer stays read-only. A comment never becomes a line of the buffer.
The view shows a comment with extmarks only: a sign on every covered row, and
a box of virtual lines below the range. The line count of the diff buffer
never changes, so the line map of the render stays correct.

The sign column shows one sign per row. The sign of a comment has a priority
above the default priority of an extmark, so the sign of another plugin on
the same row does not hide it. An example is the sign of a heading of a
markdown render plugin in a commit document.

                                                     *codeview-comments-keys*
The insert keys write comments. They do nothing in a read-only buffer, so the
diff buffer maps them to the comment editor: >

    i a         edit the comment of the line, or write the first one
    o O         write another comment on the line
    I A c       comment on the selected lines, in the visual mode
    <leader>cc  edit or write the comment of the line, or of the selection
    <leader>ce  edit the comment under the cursor
    <leader>cd  delete the comment under the cursor, after a question
    <leader>cr  resolve the comment under the cursor, or open it again
    <leader>co  open or close the comment overview
    K           show the comment under the cursor in a float
    <leader>ca  adopt the pr-agent item of the line, see |codeview-agent-adopt|.
                Only while the review holds pr-agent items.
<
A pull request review has more keys for the threads of GitHub, see
|codeview-github-threads|: >

    r           write a draft reply to the thread of the line
    <leader>cz  show or hide the comments of a resolved thread
    <leader>c+  add a reaction to a comment of the thread, or remove it
    gx          open the thread in the browser
<
`i` and `a` read the line first. A line that already holds a comment opens
that comment in the editor, the way `i` changes the text that a normal buffer
holds. A line without a comment starts a new one. `o` and `O` always start a
new comment, so a second comment on the same line stays one keypress away. A
line with more than one comment asks which comment to edit.

While the inline editor holds a comment, the diff drops the box of that
comment and keeps its sign, because the editor shows the same text one row
below the sign. The box comes back when the editor closes, in any way: a
save, a send, a discard, or a close of the window. A new comment, an edit,
and a reply end the same way, so the box looks the same after each of them.
The float editor (`comments.editor = "float"`) does not sit under the row,
so the box stays in the diff while it is open.

A row can hold the boxes of more than one comment. The inline editor of an
edit takes the place of the box that it edits, and the other boxes stay
above and below it in their usual order. The inline editor of a new comment
comes after the boxes of the row, where the box of the comment shows after
the save. No box goes under the editor window.

A delete of the comment that the editor holds also closes the editor, without
a question, because the delete asked one. The message "the open editor of this
comment closed" reports it.

The visual mode keeps `i` free, because `i` is the prefix of the text objects.
`vi(` still selects a text object in the diff buffer. The maps are
buffer-local. They never reach a file buffer of your own.

Every key comes from the `keymaps` option. Set an entry to false to disable
it, or give a list of keys for one action: >lua

    require("codeview").setup({
      keymaps = {
        comment_insert = { "i", "a" },   -- fewer insert keys
        comment_visual = false,          -- no visual mode maps
        show_comment = "gh",
      },
    })
<
                                                   *codeview-comments-editor*
The editor is a floating window with its own markdown buffer. This buffer is
the only modifiable buffer of the comment flow. You never type into the diff
buffer, and the plugin never writes to a file of the repository.

In the editor: >

    :w          save the comment
    :wq :x ZZ   save the comment
    q           discard the comment
    <Esc><Esc>  discard the comment
    <leader>cs  send the comment to the pull request
<
An empty body counts as a discard. A close of the window without a write
discards the comment too. To delete a comment, edit it, remove all of its
text, and save. The plugin deletes the comment and asks no question.

One editor is open at a time. A second open, for example `o` on another line,
replaces the editor. When the open editor holds typed text, the plugin first
asks "Discard the comment?". "No" keeps that editor, and the second open does
nothing.

Each write of the editor buffer saves the comment. The save runs from the
|BufWriteCmd| autocmd, so every command and key that writes the buffer saves
it: `:w`, `:wq`, `:x`, `ZZ`, `:wqa`, `:xa`, and a key of your own that writes.
The quit part of `:wq`, `:x`, and `ZZ` closes the editor and no other window.
`ZZ` and `:x` write only a changed buffer. An unchanged comment closes without
a save, and stays as it was.

The `editor_cancel` option names the discard keys. The `editor_save` option
is off by default. Set it to map a save key of your own, for example
`<C-s>`.

In a pull request review, the send key saves the comment and posts it to
GitHub at once, without a summary. The `editor_send` option names the key. See
|codeview-submit-send|. In a local review the key reports that the comment has
no pull request.

                                                    *codeview-comments-anchor*
The anchor of a comment comes from the line map of the render. The cursor row
gives the file line and the side:

    - A removed line anchors to the old side.
    - An added line anchors to the new side.
    - An unchanged line anchors to the new side, like the GitHub review UI.

In the side-by-side style the window under the cursor selects the side. The
left window comments on the old file, and the right window on the new file. A
comment keeps its anchor across a change of the style, because both styles
read the same file lines.

A comment on a line of a collapsed section moves its sign to the row above the
section. A section at the start of the file has no row above it, so the sign
goes on the row of the section itself. The row of the sign also answers for
the edit key and for the delete key. Press `za` to show the lines again.

                                           *codeview-comments-editor-position*
The `comments.editor` option selects where the editor opens: >

    inline    under the commented row, next to the line numbers (default)
    float     in the middle of the screen
<
Both styles have a frame, from the `comments.border` option. The frame shows
the title and the keys that save and discard. With `border = "none"` the
inline editor shows them in its winbar instead.

The inline editor opens the diff at the commented row. The space comes from
virtual lines, so the diff keeps its rows, keeps its line map, and stays
read-only. The lines under the comment move down while you type, and they move
back when you save or discard. In the side-by-side style, the other side takes
blank lines of the same height, so the two sides stay in line while the editor
is open. A window that shows no diff row opens the
float instead, for example an edit from the comment overview. An edit of a
comment of another file than the open diff opens the float too.

When the window under the inline editor closes, the editor closes too. When it
holds typed text, the plugin first asks "Discard the comment?". "No" keeps the
editor and moves it to the float, because its window is gone.

The editor starts in insert mode, after the last character of the text. Set
`comments.start_insert` to false to start in normal mode.

                                                   *codeview-comments-display*
The `comments.display` option selects the display: >

    virtual   the body shows in a box of virtual lines below the range
              (default)
    float     the row keeps the sign only
<
The `K` key shows the comment in a float in both cases.

                                                       *codeview-comments-box*
With `display = "virtual"` a comment shows as a box with a frame and a
background of its own, the same as the inline editor: >

    ╭─ comment L2 (new) ──────────────────────────╮
    │ please rename this                          │
    ╰─────────────────────────────────────────────╯
<
The header goes into the top border. The box is as wide as the diff window,
minus the line numbers and the sign column, minus one column. It is never
less than 20 columns. In the side-by-side style each box takes the width of
its own window. When a window changes size, for example when the sidebar or
the overview opens or closes, the boxes take the new width.

A body line that is too long wraps inside the box, at the spaces between the
words. A word that is wider than the box breaks at the edge. A header that is
too long ends in "…".

The frame follows the `comments.border` option: "rounded", "single",
"double", "bold", and "solid" draw a frame. "none", "", and "shadow" draw no
frame. The box is then the header line and the body lines, still with the
background. A border name that the box does not know draws a "single" frame.

The background comes from |hl-CodeViewCommentBox|, a light blue tint in most
colorschemes, and the frame from |hl-CodeViewCommentBorder|. A comment from
GitHub takes |hl-CodeViewRemoteBox| and |hl-CodeViewRemoteBorder|, a grey
tint, so it looks different from your own comments. A pr-agent item takes
|hl-CodeViewAgentBox| and |hl-CodeViewAgentBorder|. See |codeview-agent|.

                                                     *codeview-comments-state*
A comment holds a state: "open" or "resolved". The resolve key changes the
state, and the state goes into the `state` field of the comment, so it
survives a restart. A resolved comment takes the sign of the
`comments.resolved_sign` option, and its header line says "resolved". Use the
comment overview to walk the open comments of the review. See
|codeview-overview|.

In the side-by-side style a comment keeps the two windows aligned. The other
side takes virtual lines of the same number, without text, so both windows
grow by the same height. The sign column of a split window has a fixed width,
so a sign on one side does not move the text of that side alone.

                                                     *codeview-comments-store*
The comments of one session live in one markdown file. The directory comes
from the `comments.dir` option and from the path of the repository. The file
name is a hash of the repository root and of the resolved range, so a reopen
of the same range finds the file again: >

    ~/.local/share/nvim/codeview/review/<repo-slug>-<hash>/<session-key>.md
<
The frontmatter of the file holds the session data. Each comment is one
section with a field block and a markdown body: >

    ---
    version: 1
    key: 4f1c0a2b8d3e5f60
    repo: /home/ada/code/demo
    range: aaaa1111..bbbb2222
    spec: main..@
    created_at: 2026-08-12T09:00:00Z
    updated_at: 2026-08-12T09:30:00Z
    ---

    # codeview review: main..@

    ## codeview-comment 68a1c2f30b7a

    - file: lua/codeview/store.lua
    - start_line: 12
    - end_line: 14
    - side: new
    - commit: bbbb2222
    - state: open
    - synced_at:
    - review_id:
    - created_at: 2026-08-12T09:10:00Z
    - updated_at: 2026-08-12T09:10:00Z
    - remote_id:

    The body of the comment.
<
A draft reply to a thread of GitHub holds one more field, after `remote_id`: >

    - reply_to: 1680042137
<
The fields hold: >

    file          path of the file in the new revision
    start_line    first line of the comment, in the file at `commit`
    end_line      last line of the comment
    side          "old" for a removed line, "new" for every other line
    commit        revision that the lines come from
    state         "open" or "resolved"
    synced_at     time of the submit that sent the comment to GitHub
    review_id     review of GitHub that holds the comment
    created_at    time of the first save
    updated_at    time of the last change
    remote_id     id of the comment on GitHub
    reply_to      id of the first comment of the GitHub thread that the
                  comment replies to. Only a reply holds this field.
<
The three sync fields stay empty until a |:Codeview-submit| confirms the post.
A comment that goes into the text of a review keeps an empty `remote_id`. A
file of an older release has no `remote_id` field, and the plugin reads it
with an empty one. See |codeview-submit-state|.

The plugin writes the `reply_to` line only for a reply. A file without
replies therefore stays the same as the file of an older release. A file
without the field reads with an empty `reply_to`. The `version` stays 1.

The plugin writes the file atomically. It writes a temporary file in the same
directory and renames it over the target. A failed write keeps the file of the
last save.

Read the store from Lua with |codeview.store()|.

                                                             *codeview-hints*
A row at the bottom of the screen shows the keys of the window that has the
cursor, the way a terminal tool does: >

     ]h next hunk  ]f next file  za unfold  <space>ct style  K read comment
<
The row holds the keys that a reader does not guess from the window. `i`
writes a comment and `<CR>` opens the file under the cursor, so neither reads
in the row. The style toggle does read there, because nothing else names it.

The row is a window of one line, and not a float, so it covers no line of a
diff and no statusline. It opens with the session and closes with it. It
follows the `keymaps` option, so it names the keys that you set. The row
changes when the cursor enters another window or buffer. A cursor move inside
a window does not draw it again.

Set `hints.enabled` to false to leave the row out. Set `hints.actions` to name
the actions of one surface yourself. The surfaces are "sidebar", "view", and
"overview": >lua

    require("codeview").setup({
      hints = {
        actions = {
          view = {
            { action = "toggle_style", text = "style" },
            { action = "toggle_overview", text = "comments" },
          },
        },
      },
    })
<

9. COMMENT OVERVIEW                                          *codeview-overview*

The comment overview lists every comment of the session in one panel. Open it
with |:Codeview-comments|, or with `<leader>co` from the sidebar and from the
diff. Set `overview.auto_open` to true to open it with every |:Codeview|.

The overview groups the comments in the same tree as the changed-files
sidebar. A comment is a child of its file. Every node shows the number of
comments below it: >

    9b2688a5..ec056be0
    3 comments, 1 resolved

      ▾ lua/codeview 1
      │ ▾ store.lua 1
      │ │ ✓ L5 new 4f1c0a2b rename this function
      ▾ call.lua 2
      │ ▌ L1 new 4f1c0a2b the first note
      │ ▌ L2-3 old 4f1c0a2b two lines
<
One comment line holds the sign of the state, the line range, the side, the
short commit with 8 characters, and the first line of the body. A body that is wider than the
panel ends with an ellipsis. The sign comes from the `comments.sign` option
for an open comment, and from the `comments.resolved_sign` option for a
resolved comment.

                                                    *codeview-overview-keymaps*
The overview buffer holds these maps. |codeview-config| names the keys: >

    <CR>        open the comment in the diff, or toggle a directory
    <Tab>       show or hide the comments of the file under the cursor
    zR          show the comments of every file
    zM          hide the children of every node
    <leader>ce  edit the comment under the cursor
    <leader>cd  delete the comment under the cursor, after a question
    <leader>cr  resolve the comment under the cursor, or open it again
    <leader>ca  adopt the pr-agent item under the cursor as a comment, only
                while the review holds pr-agent items
    <leader>cx  show the markdown of the comments in a scratch buffer
    <leader>cy  write the markdown of the comments into the register
    <leader>cR  read the review again from the repository
    <leader>co  close the overview
    q           close the overview
<
`q` closes the overview only. The session stays open, and the changed-files
sidebar stays open. A `:q` in the overview does the same. |codeview.overview()|
then gives nil, and the closed overview follows no event of the comments.

                                                    *codeview-overview-export*
`<leader>cx` shows the markdown of the export in a scratch buffer. The buffer
holds every comment of the session, so you copy one part of the text or the
whole text. See |codeview-export|.

`<leader>cy` writes the same markdown into the register of the
`export.register` option. That register is "+" by default, so the key writes
the review to the clipboard of the system. The key opens no buffer, and the
cursor stays in the overview.

                                                      *codeview-overview-jump*
`<CR>` on a comment opens the diff of its file and moves the cursor to the
anchor of the comment. A collapsed section that hides the line shows its lines
again. In the side-by-side style the cursor goes to the window of the side of
the comment. `<CR>` on a file line opens the first comment of the file.

A file that the range does not change any more keeps its comments, but the
jump key cannot open it. The overview shows the name of such a file dim.

                                                    *codeview-overview-events*
Every change of a comment sends an event. The overview and the diff view
subscribe to it, so a delete in the overview clears the extmarks of the diff
at once, and a comment in the diff shows in the overview at once. Each event
also runs a |User| autocmd: >

    CodeViewCommentAdded      a new comment went into the store
    CodeViewCommentChanged    the body or the state of a comment changed
    CodeViewCommentDeleted    a comment left the store
    CodeViewReviewSubmitted   a submit or a send posted comments to GitHub
<
The payload holds the id of the comment, the file, the id of the session, and
the state: >lua

    vim.api.nvim_create_autocmd("User", {
      pattern = "CodeViewCommentAdded",
      callback = function(event)
        vim.print(event.data.file, event.data.id)
      end,
    })
<

10. EXPORT                                                     *codeview-export*

The export renders the comments of the session as markdown. Run
|:Codeview-export|. The text goes into a scratch buffer and into a register,
so you paste the review into a chat window or into a pull request description.

The comment overview holds the same two actions on keys. `<leader>cx` shows
the export in a scratch buffer, and `<leader>cy` writes it into the register
only. See |codeview-overview-export|.

The `rex-codeview` agent skill of this repository hands a review from an
agent to codeview in a Rex pane, and reads the export back. See
|codeview.review()|. The script of the skill rejects a revision that starts
with `-`, because Neovim and git read such an argument as an option.

The default template is plain markdown: >markdown

    # codeview review: main..@

    A code review of this change produced the comments below. Each comment
    names its lines, its side of the diff (old or new), and the commit that
    holds the lines. Make the change that each comment asks for. Skip only
    a comment that is marked resolved.

    - range: `9b2688a5..ec056be0`
    - commits: 2
    - comments: 3 on 2 files, 1 resolved

    ## `call.lua`

    ### L1 · new · ec056be0

    the first note

    ### L2-3 · old · 9b2688a5 · resolved

    two lines
<
Each comment holds its line range, its side, and the commit of the lines. A
reader finds the code with those three values, without the plugin. `L1` is the
line in the file at that commit. The side is "new" for an added line or for an
unchanged line, and "old" for a removed line. A resolved comment holds the word
"resolved" in its header.

The path of a file heading is a code span, so a path with markdown in it, for
example `pkg/__init__.py`, keeps its characters. An old-side comment on a
renamed file also names the old path in its header, because its lines come
from that file: >markdown

    ### L4 · old · `lua/old_name.lua` · 9b2688a5
<
A body with a markdown heading line goes into a fenced block, so its lines
cannot start a new section of the export. Every other body stays as it is.

The files come in the order of the changed-files sidebar, and the comments of
one file come in line order. A file with comments that the range does not
change any more comes last, with the note "(outside the range)".

`q` closes the window of the export buffer. A second export of the same session
replaces the buffer of the first one. |:Codeview-close| closes the export
window with the other windows of the session.

                                                      *codeview-export-prompt*
The `export.prompt` option holds the text under the title of the export. The
default text says that a code review produced the comments below. It tells the
reader to make the change that each comment asks for, and to skip only a
comment that is marked resolved. As a result, an agent that reads the export
acts on the comments without more instructions.

Set the option to replace the text: >lua

    require("codeview").setup({
      export = { prompt = "Fix every comment below." },
    })
<
An empty text writes no prompt. The export then starts with the title and the
metadata lines. A template reads the same text in `data.prompt`, so a custom
renderer keeps the prompt. See |codeview-export-template|.

                                                     *codeview-export-register*
The `export.register` option names the register. The default is "+", the
system clipboard. Set the option to another name to keep the clipboard free:
>lua

    require("codeview").setup({ export = { register = "z" } })
<
An argument of the command wins over the option. An empty option writes no
register. The name must be one register character. A longer text writes no
register and gives a warning. "+" and "*" need a clipboard tool. Without one
the export writes no register and gives a warning. See |clipboard|.

                                                     *codeview-export-template*
The `export.template` option replaces the default template. The function gets
the session and the data of the export, and returns the text: >lua

    require("codeview").setup({
      export = {
        template = function(session, data)
          local lines = { "# " .. session:label() }
          for _, comment in ipairs(data.comments) do
            local at = comment.file .. ":" .. comment.start_line
            lines[#lines + 1] = at .. " " .. comment.body
          end
          return table.concat(lines, "\n")
        end,
      },
    })
<
The data table holds these fields: >lua

    data.session    -- session of the export
    data.store      -- comment store of the session
    data.spec       -- text that names the range
    data.range      -- resolved range, with short revision ids
    data.repo       -- absolute path of the repository root
    data.prompt     -- text under the title, from the export.prompt option
    data.files      -- files with comments, each with its comment list
                    -- and `old_path`, the old path of a renamed file
    data.comments   -- every comment, in the order of the render
    data.count      -- number of comments
    data.resolved   -- number of resolved comments
<
A template that fails, or that gives a value that is not a text, falls back to
the default template. The plugin reports the problem.

11. PULL REQUESTS                                              *codeview-github*

`:Codeview pr {number}` reviews a pull request of GitHub. The review reads and
writes nothing on GitHub: it holds your comments in the session file, like a
local review. |:Codeview-export| gives you the text for the web page.

The command needs the gh CLI in $PATH, and a login. Run `gh auth login` once.
`:checkhealth codeview` reports both. See |codeview-health|.

The `github.binary` option names that executable. See |codeview-binaries|.

                                                        *codeview-github-host*
Every API call goes to the host of the address of the pull request, through
`gh api --hostname`. A pull request on a GitHub Enterprise host therefore gets
the token of that host. A call that writes, for example a submit, gets a time
limit of 120 seconds, because a review with many comments takes GitHub more
time. `require("codeview.gh").write_timeout` holds the limit, in milliseconds.

                                                      *codeview-github-errors*
A failed call gives one message. These failures have their own error code: >

    not_authenticated   gh has no valid token for the host (HTTP 401)
    rate_limited        the rate limit of GitHub is used up
    offline             the call did not reach the host
    unsupported         gh is not in $PATH
<
Only HTTP 401 means a missing login. Another refusal of GitHub, for example
HTTP 403 on a repository without access, gives the message of GitHub.

The callback of a GitHub call always runs later, on the main loop. This is
also true for an error that the call finds before it starts gh.

                                                     *codeview-github-loading*
The command needs the network before it can show a diff. While it works, a
float in the middle of the editor shows the pull request and these steps:
find the repository, read the pull request, fetch the commits, find the diff
range, and open the review. A spinner turns on the step that runs, and a check
mark stands on each step that ended. The float closes before the review
windows open. The float does not take the cursor while the steps run.

If a step fails, the float stays. It marks the step with `✗` and shows the
error, and the cursor goes into it. Press `q` or `<Esc>` to close it. The
float is the report of the error, so the command sends no message for it. The
|hl-CodeViewLoadingDone| and |hl-CodeViewLoadingFailed| groups color the marks.

                                                        *codeview-github-refs*
The working copy does not change. The command fetches two refs of the plugin
and checks out no branch: >

    refs/codeview/pr/{number}/head    the commits of the pull request
    refs/codeview/pr/{number}/base    the tip of the base branch
<
The review range is `base...head`, so it starts at the merge base of the two
refs. That is the range of the "Files changed" tab of GitHub. The sidebar
header shows the number and the title of the pull request.

                                                    *codeview-github-document*
The sidebar lists the pull request itself as the first entry, under the node
"Pull request". The document shows the title, the author, the branches, the
state, the link to the web page, the description, and the commits. Press
`gx` on the link to open the pull request in the browser.

A comment on this document is an overall comment on the pull request. The
send key of the editor posts it to the conversation of the pull request. A
submit of the session takes it as the text of the review. See
|codeview-submit|.

A pull request review needs a git repository. A colocated jj repository holds
one, so it works there too.

The `github.remote` option names the git remote of the fetch. An empty text
lets the plugin pick the remote:

    1. The remote whose URL names the repository of the pull request. The
       SSH, HTTPS, and scp forms all match, with or without `.git`. A remote
       on the host of the pull request comes before one on another host.
    2. Else, when the `repo` option of |codeview.open_pr()| names the
       repository, the HTTPS URL of that repository on the host of the pull
       request.
    3. Else the first of `upstream`, `github`, and `origin`.
    4. Else the first remote of the repository.

When more than one remote matches in step 1, the order of step 3 decides.
The head that the fetch gives must be the head commit that GitHub reports. A
push between the two reads gives another commit, and the open stops with a
message. Open the pull request again.

                                                       *codeview-github-fetch*
GitHub reports the head commit and the base commit of the pull request. When
the repository holds both commits already, the command writes the two refs from
them and skips the fetch. The review then opens without a wait for the network.
A tool that fetched the pull request before, for example chaoshub, gives you
this case. Set `github.fetch` to "always" to fetch every time. Without the
fetch, the command does not see a base branch that the remote deleted, so it
shows no warning for it.

                                                       *codeview-github-store*
The session key of the comment file is `pr-{number}-{head commit}`. A new push
to the pull request gives a new head commit, so the next review starts with an
empty comment file and your notes on the older push stay where they are. See
|codeview-comments-store|.

                                                     *codeview-github-remote*
The review comments of the pull request come in after the session opens. The
diff shows them under their line, with the sign of the `comments.remote_sign`
option and the login of the author. Each thread shows in one box with a grey
tint, the same box as a local comment. See |codeview-comments-box|. The
comment overview lists the threads in a section of their own, under the local
comments.

                                                    *codeview-github-threads*
A thread is the first review comment on a line and the replies to it. The box
of a thread holds the first comment at the top, then the replies, oldest
first. A line with a divider and the login of the author starts each reply. A
comment with reactions ends with one line of them, for example `👍 2  🎉 1`.

All boxes that end on one row of the diff share one extmark (a mark that
Neovim keeps on a buffer row). The order of the boxes is the time of their
first comment, oldest first. As a result, the order on the screen is always
the order of time.

A resolved thread shows one header line only: >

    ✓ resolved · @alice L12 (new) · 3 comments
<
`<leader>cz` on the line shows every comment of the resolved thread, and a
second `<leader>cz` hides them again. `K` always shows the whole thread in a
float, oldest comment first, with the reactions.

codeview reads the thread state with the GraphQL API of GitHub: the resolved
state, your rights on each comment, and the reactions. If this read fails, the
review shows the comments without the thread state, and one warning tells
you. The thread keys then report "the thread state of GitHub is not
available".

                                                      *codeview-github-reply*
To reply to a thread, do these steps:

1. Put the cursor on the line of the thread.
2. Press `r`. The editor opens under the thread, with the title
   `Reply to @author`. If more than one thread covers the line, a picker asks
   which one.
3. Write the reply and save it with `:w`.

The reply is a draft. It is a local comment with the field `reply_to` in the
session file, see |codeview-comments-store|. It shows in the box of the
thread, with the word "draft". `i`, `a`, `<leader>ce`, and `<leader>cd` edit
and delete a draft reply, the same as any local comment.

A draft reply goes to GitHub with the send key of the editor, with
|:Codeview-submit|, or through the bridge of another tool, see
|codeview-bridge|. After the send, the reply shows in the thread on GitHub and
in codeview with the word "synced", once. A reply to a thread that the session
does not hold shows in a box of its own, with the word "reply".

                                                    *codeview-github-actions*
The other thread actions go to GitHub at once. Only a reply waits for a send.
On a line without a local comment, these keys act on the thread: >

    <leader>cr  resolve the thread, or open it again
    <leader>ce  edit the text of a comment of your own
    <leader>cd  delete a comment of your own, after a question
    <leader>c+  add a reaction to a comment, or remove your own reaction
    gx          open the first comment of the thread in the browser
<
On a line with a local comment, `<leader>cr`, `<leader>ce`, and `<leader>cd`
act on the local comment, as before. `<leader>c+` and `gx` always act on the
thread, because they do not apply to a local comment. Without a thread under
the cursor, `gx` opens the file name or the address under the cursor, the
same as the default `gx` of Neovim.

The edit key opens the editor with the text of your comment. If the thread
holds more than one comment of yours, a picker asks which one. A save sends
the new text to GitHub at once. A save of an empty text changes nothing.

The reaction key asks for the comment when the thread holds more than one,
then for the reaction. Your own reactions carry a `✓` in the picker. If you
pick one of them, codeview removes it. Else codeview adds the reaction.

GitHub decides who can resolve a thread, reply to it, or change a comment. A
key that GitHub does not permit reports that and changes nothing. After a
change, codeview reads the threads again.

In the comment overview, the same keys act on the thread under the cursor:
`<leader>cr`, `<leader>ce`, `<leader>cd`, `r`, `<leader>c+`, and `gx`.

GitHub reports the lines of a comment in the newest version of the diff. A
comment over lines of both sides keeps its last line only, because one anchor
holds the lines of one side.

A comment that a later push moved is outdated. GitHub then gives only the
lines of an older version, and those lines can hold other text now. The diff
looks for the last lines of the `diff_hunk` of the comment in the current
file. With one clear match the comment shows on those lines, with the word
"outdated". Without one, no row of the diff holds the comment. The overview
lists it with the word "outdated" and without line numbers. `<CR>` on it opens
the diff of the file, but moves the cursor to no line.

A comment that a submit of this session sent lives on GitHub and in the
session file. The review drops the copy of GitHub and keeps the local comment
with the word "synced", so the comment shows once. A local comment with a
`remote_id` is the copy of the GitHub comment with that id.

Set `github.comments` to false to leave the review comments out. The option
`github.max_comments` limits the number of comments of one fetch. A pull
request with more comments gives a warning: the review shows the oldest
comments, up to the limit. Raise the option to read more.

A failed fetch of the comments gives one message. The review itself stays
open, because it needs no network after the fetch of the refs.

|:Codeview-submit| sends your comments to the pull request. See
|codeview-submit|.

                                                             *codeview-agent*
chaoshub runs pr-agent on a pull request and writes the results to JSON
files. pr-agent writes nothing to GitHub. A review of the pull request reads
these files. The results are read-only.

                                                     *codeview-agent-without*
codeview does nothing for a pull request without result files. It creates no
file and no directory under the root. Without the root, it starts no
watcher. The review then shows no "Agent" node, no overview section, no sign,
and no box. It sends no `CodeViewAgentLoaded` event, and it maps no adopt key.
A missing file gives no warning.

The files of a pull request are in `<root>/<owner>/<repo>/<number>/`, one
file per tool: `review.json`, `improve.json`, `describe.json`, and
`ask.json`. The root is the first of these:

    1. The `github.agent_dir` option, when it is not empty.
    2. `$CHAOSHUB_AGENT_ROOT`. chaoshub sets it for a review that it opens.
    3. `$XDG_STATE_HOME/chaoshub/agent`.
    4. `~/.local/state/chaoshub/agent`.

Each file holds one JSON object: >

    version       1, the version of the format
    tool          review, improve, describe, or ask
    pr            number of the pull request
    head_sha      head commit of the pull request when the run started
    model         name of the model
    started_at    time of the start of the run
    finished_at   time of the end of the run
    usage         token counts of the run
    data          JSON of pr-agent. For ask, a list of questions and
                  answers, newest first
<
A file of another `version` gives one warning, and the review leaves it out.

The results load with the review of the pull request. They load again after
each refresh of the review, and after each change of the directory: a watcher
follows the directory, so a run of chaoshub reaches the open review.

When the directory of the pull request does not exist, the watcher follows
the deepest directory of the path that exists: the root, `<owner>`, or
`<repo>`. When the next part of the path comes to exist, the watcher moves
down. The first run of chaoshub then reaches the open review without a
refresh. When the root does not exist at the open, a refresh starts the
watcher after chaoshub made the root.

A read that finds a change of the results sends the |User| event
`CodeViewAgentLoaded`, and so does each adopt of |codeview-agent-adopt|. A
read without a change sends no event and draws nothing again.

                                                   *codeview-agent-documents*
The sidebar lists the review, the describe, and the ask result as documents,
under the node "Agent", between the pull request document and the commits: >

    ▾ Pull request
        #12 Add a greeting
    ▾ Agent
        Review
        Describe
        Ask
    ▾ Commits
<
A tool without a result gets no document. The review document shows the
fields of the review and the key issues with their files and lines. The
describe document shows the new title and the new body. The ask document
shows the questions and the answers, newest first.

pr-agent writes markdown, so a pr-agent document has the `markdown`
filetype, as a commit document does. The text of a key issue, the new body,
and each answer have no indent. The other lines are plain text. See
|codeview-commit-message|. A result of an older head of the pull request
says so in its first line: >

    Outdated: pr-agent ran on 3a1f2c0, the head is now 9bd2e11.
<
A comment on a pr-agent document stays local. A submit does not send it.

                                                     *codeview-agent-diff*
The improve suggestions, and the review key issues that name a file and
lines, show in the diff like the comments of GitHub: a sign of the
`comments.agent_sign` option on each line, and a box of virtual lines under
the last line. The header of an item reads: >

    pr-agent · possible issue · score 8 · L12-14 · read-only
<
The virtual lines of a suggestion hold its text and the improved code. `K`
shows the item in the float, next to the comments of the line. An item is
read-only: the edit key, the delete key, and the resolve key report that.

A result of an older head is outdated. The diff then looks for the
`existing_code` of a suggestion in the current file. With one clear match the
item shows on those lines, with the word "outdated". Without one, no row of
the diff holds the item. A key issue holds no code, so an outdated issue
shows in the overview only.

The comment overview lists the items in a section "N agent suggestions",
after the section of the comments of GitHub. `<CR>` on an item opens its line
in the diff. The |hl-CodeViewAgent|, |hl-CodeViewAgentHeader|, and
|hl-CodeViewAgentSign| groups color the items. An item in the diff shows as a
box, the same as a comment of GitHub, with its own tint from
|hl-CodeViewAgentBox| and |hl-CodeViewAgentBorder|. See
|codeview-comments-box|.

                                                    *codeview-agent-adopt*
`<leader>ca` takes a pr-agent item as a comment of your own. The key works in
the diff on a line of the item, in the float of `K`, and in the comment
overview on the line of the item. It adds a local comment on the same lines,
and opens it in the editor, so that you can change the text. The item then
shows as "adopted".

The adopt key exists only while the review holds pr-agent items. Without
them, codeview maps no `<leader>ca`, so the key keeps your own map, for
example the code action of your LSP client. The hint row shows the key only
then too. When results arrive in an open review, the key comes to the open
diff and to the comment overview.

The body of a suggestion is its text, then a `suggestion` block with the
improved code: >

    Trim the name before the greeting uses it.

    ```suggestion
    format!("Hello {}", name.trim())
    ```
<
GitHub shows such a block as a change that the author can apply. The body of
a key issue is the text of the issue. |:Codeview-submit| posts the comment
like any other comment. An outdated item that the diff holds no line for
cannot be adopted.

12. SUBMIT                                                     *codeview-submit*

|:Codeview-submit| sends the comments of the session to the pull request. The
comments go out as one review. The pull request then shows one entry with all
the lines.

The command needs a session of |:Codeview-pr|. A local review has no pull
request, so the command reports that and stops.

The post is always explicit: >

    1. The command collects the comments that no submit sent yet.
    2. It asks for the event of the review.
    3. It asks for the text of the review.
    4. It shows the summary: every comment that goes out, and every comment
       that stays local.
    5. It posts after you pick "submit".
<
Nothing reaches GitHub before that pick. No autocommand and no write of a
file posts by itself. The send key of the editor is the one key that posts,
and it posts one comment. See |codeview-submit-send|.

A comment on the pull request document goes into the text of the review. The
command then asks for no text, and the summary lists the comment under the
line "into the text of the review".

`:Codeview submit {event}` skips the question about the event. The events are: >

    comment           the review adds comments only
    approve           the review approves the pull request
    request-changes   the review asks for changes
<
`:Codeview! submit` skips the question about the text of the review. GitHub
needs a text for the comment event and for the request-changes event, so the
review then holds one default line.

                                                        *codeview-submit-send*
The send key of the comment editor, `<leader>cs` by default, saves the
comment and posts it at once. It posts that one comment only, so it shows
no summary. A comment on a line goes to the review comments of the pull
request. A comment on the pull request document goes to the conversation of
the pull request. A comment on a commit message stays local, because GitHub
has no place for it.

The comment gets the sync state of a submit after GitHub confirms the post.
See |codeview-submit-state|. A failed post marks nothing, and the report
holds the answer of the server.

                                                    *codeview-submit-position*
The position of a comment comes from a line map of the diff. The map runs with
the diff settings of git, the myers algorithm with the indent heuristic, and
without the line alignment of the display, because GitHub takes only the lines
of the diff of git. The review itself shows the histogram diff, which reads
better. The map gives the fields of the review API of GitHub: >

    side          LEFT for the old side, RIGHT for the new side
    line          last line of the comment
    start_line    first line of a comment over more than one line
    start_side    side of the first line
<
GitHub takes a comment only on a line of its diff. A comment on another line
stays local. The summary names that comment with the reason. These comments do
not map: >

    - the pull request does not change the file any more
    - the diff of the pull request does not hold the line
    - the line range of the comment is not one block of the diff
<
Move such a comment to a line of the diff, or read it with |:Codeview-export|.

The diff of GitHub keeps three unchanged lines around each change. The review
buffer can show one line more, because it hides no section of one line. A
comment on such a line stays local, and the summary names it. The submit
reports the line before the post. It does not send a line that GitHub rejects.

                                                       *codeview-submit-state*
A comment carries its sync state in the session file: >

    - synced_at: 2026-08-13T09:41:12Z
    - review_id: 2371558991
    - remote_id: 1680042137
<
A comment gets these fields only after GitHub confirms the post. The next
submit then leaves this comment out, so no comment goes out twice. The diff
and the comment overview show the word "synced" on it.

An edit of the text clears the sync time. The pull request holds the text of
the last submit, so the next submit sends the new text. It changes the text of
the comment on GitHub with a PATCH call, through `remote_id`, and posts no new
comment.

A move of the anchor (the file, the side, or the lines) also clears the sync
time. GitHub cannot move a comment, so the move clears `remote_id` too, and the
next submit posts a new comment.

A draft reply holds a `reply_to` field, see |codeview-github-reply|. The
submit posts it after the review and after the edits, one reply at a time,
into its thread. The summary names it as `reply to @author: <text>`. A reply
that GitHub took gets the three sync fields. The first failure stops the
other replies, and they stay unsent. A submit of edits and replies alone asks
for no event and no text, only for the confirmation.

                                                       *codeview-submit-guard*
A post that the time limit stopped can still reach GitHub. Before a review
post, the submit therefore lists the reviews of the pull request. A review of
your login, on the same commit, with the same text and the same comments, is
the review of an earlier try. The submit then marks the comments as sent and
posts nothing. The `existing` field of the result is true in that case.

One session runs one submit or one send at a time. A second call while the
first one runs gives an error, so no comment goes out twice.

Another Neovim can send the comments of the same session file, for example
the headless codeview of |codeview-bridge|. These rules keep each comment to
one send:

- The session file is the truth. A comment with a `synced_at` value in the
  file went out, and no submit and no send posts it again.
- A save reads the file first and keeps its sent marks. An open session
  never writes its old copy over the marks of another send.
- A submit and a send read the sent marks of the file before they choose
  the comments.
- An open session watches its session file. When another Neovim marks a
  comment as sent, the diff and the overview show it as sent.
- A submit and a send make the lock file `<session-key>.md.lock` next to the
  session file. It holds the pid and the time. While another Neovim holds
  the lock, the call stops with the error "another codeview sends these
  comments now. Try again when it is done". A lock older than 10 minutes,
  or a lock of a pid that does not run, is stale, and the call replaces it.
  The lock goes away at the end of the call, also after an error.

A failed post writes nothing. No comment gets the fields, and the session file
does not change. The report holds the answer of the server, for example the
line that GitHub did not take. Correct the comment, then run the command
again.

A submit sends the event CodeViewReviewSubmitted. See
|codeview-overview-events|.

                                                             *codeview-bridge*
Another tool can show the comments of codeview and send some of them. chaoshub
does this. The tool reads the session file, see |codeview-bridge-file|. It
never writes it. To send, the tool runs codeview in a headless Neovim, with
the repository as the working directory: >

    nvim --headless -c "lua require('codeview.bridge').submit_file('<path>')"
<
codeview then maps the comments to the lines of the diff, posts one review,
and marks the comments as sent. The lock and the sent marks of
|codeview-submit-guard| cover this send too.

The file at `<path>` holds the request, as JSON: >json

    {
      "version": 1,
      "repo": "owner/name",
      "number": 14,
      "head": "<sha>",
      "ids": ["68a1c2f30b7a"],
      "event": "comment",
      "body": "",
      "out": "/tmp/result.json"
    }
<
The fields hold: >

    version       1
    repo          repository of the pull request, as owner/name
    number        number of the pull request
    head          head commit that the comments belong to
    ids           ids of the comments to send
    event         "comment", "approve", or "request-changes"
    body          text of the review, "" when it is not given
    out           path of the result file
<
The call opens the pull request session without the layout. When the head of
the pull request is not `head`, the call stops with an error, because the
comments belong to another push. It then sends the chosen comments, without
questions: the tool asked the user already. A chosen comment that went out
already does not go out again.

The call writes the result atomically to `out`, as JSON: >json

    {
      "version": 1,
      "ok": true,
      "posted": 3,
      "skipped": [{ "id": "68a1c2f30b7b", "reason": "..." }],
      "already_sent": ["68a1c2f30b7c"],
      "url": "https://github.com/owner/name/pull/14#pullrequestreview-1",
      "error": ""
    }
<
The fields hold: >

    version       1
    ok            true when the send ran without an error
    posted        number of comments that GitHub took
    skipped       comments that stay local, with the reason
    already_sent  chosen comments that went out already
    url           address of the review, "" when GitHub sent none
    error         text of the error, "" when ok is true
<
When every chosen comment went out already, the call posts nothing. The
result then has `ok` true and `posted` 0. When another Neovim holds the lock,
the result has `ok` false and the error of the lock.

The call then closes the session and quits Neovim. The exit codes are: >

    0             ok is true
    1             ok is false, or the call wrote no result file
<
Every error, also a Lua error, writes a result with `ok` false and the text
of the error.

The request, the result, and the exit codes are a stable interface within
version 0.x.

                                                        *codeview-bridge-file*
The session file is a read interface for other tools, stable within version
0.x. Its format is in |codeview-comments-store|. A tool reads it like this:

- The file is `<session-key>.md` in one directory per repository, under the
  `comments.dir` option. `~/.local/share/nvim/codeview/review/` by default.
- The frontmatter holds `version`, `repo`, and `range`. `repo` is the
  absolute path of the repository root. A tool reads only `version: 1`.
- For a pull request, `range` is `pr-<number>-<head sha>`. Each push of the
  head therefore gets a new file.
- Each comment starts with the line `## codeview-comment <id>`. The `- key:
  value` lines follow, then the body.
- A body line that starts with `\` loses that first character. The escape
  keeps a body line that reads as a comment heading out of the headings.
- A comment is unsent while its `synced_at` value is empty.
- A `- reply_to: <id>` line marks a draft reply to a thread of GitHub. Only a
  reply holds this line. It belongs to the field block, not to the body.
- A `file` of `codeview://pr/<number>` is a comment on the pull request
  document. It goes into the text of the review. A `file` of another
  `codeview://` form is a comment on a commit message. GitHub takes no such
  comment. Every other `file` is a path in the repository.

13. LUA API                                                       *codeview-api*

                                                         *codeview-api-stable*
These calls are stable: |codeview.setup()|, |codeview.open()|,
|codeview.review()|, |codeview.open_pr()|, |codeview.close()|,
|codeview.reopen()|, |codeview.session()|, |codeview.comments()|,
|codeview.export()|, |codeview.export_text()|, |codeview.submit()|, and
|codeview.refresh()|. Their names, arguments, and results stay the same
within version 0.x.

Every other call of the `codeview` module is unstable before version 1.0. It
can change in any release before 1.0. Its doc comment in
`lua/codeview/init.lua` says so. Some calls return internal tables, for
example a session or a view state. Read only the fields that this file names.

                                                        *codeview-modules*
The modules under `codeview.*`, for example `codeview.view` or
`codeview.anchor`, are internal. Call them at your own risk: they can change
in any release. The comment code lives in `codeview.comments`, with the
anchors in `codeview.anchor` and the extmarks in `codeview.marks`. The map of
an anchor to a position of the GitHub diff lives in `codeview.position`. Every
message of the plugin goes through `codeview.notify`, which reads the
`log_level` option.

                                                             *codeview.open()*
codeview.open({spec}, {opts}, {cb})
    Open a review session for {spec}. {spec} is revision text such as "HEAD"
    or "main..feature", or a table with resolved revisions.

    {opts} accepts these fields: >lua

        {
          repo = nil,     -- repository handle, to skip the detection
          dir = nil,      -- directory for the detection, cwd by default
          backend = nil,  -- "auto" | "git" | "jj", the config value by default
          export_file = nil, -- path of a file for the export of the session
          quit = nil,        -- true quits Neovim when the review ends
        }
<
    Without {cb} the call blocks and returns `session, err`. With {cb} the
    call returns at once and calls `cb(session, err)`.

    With `export_file`, the session keeps its export in that file. See
    |codeview.review()|.

                                                           *codeview.review()*
codeview.review({spec}, {opts})
    Open a review the way |:Codeview| {rev} does. The call opens the session,
    the sidebar, the overview, and the hints, and it shows the summary of the
    session. It returns at once. If the open fails, you get the error as a
    message, the same as from |:Codeview|.

    {opts} accepts these fields: >lua

        {
          dir = nil,         -- directory for the detection, cwd by default
          export_file = nil, -- path of a file for the export of the session
          quit = nil,        -- true quits Neovim when the review ends
        }
<
    With `export_file`, the session writes its export to that file. The
    first write comes right after the open, also without comments. The
    session writes the file again after each change of a comment, and after
    each refresh. As a result, the file holds the last state of the review
    after every exit: `:qa`, `:qa!`, |:Codeview-close|, or a closed terminal.
    The file has the format of |codeview-export|. If a write fails, you get
    a warning, and the review continues.

    With `quit = true`, Neovim quits when the review ends, the same as
    `++quit` of |codeview-quit|. A second review in the same Neovim does not
    end it. `quit = false` works as `++noquit`. Without the field, Neovim
    stays open.

    A tool outside Neovim starts a review with an export file: >sh

        nvim -c "lua require('codeview').review('main..@',
          { export_file = '/tmp/review.md', quit = true })"
<

                                                          *codeview.open_pr()*
codeview.open_pr({number}, {opts}, {cb})
    Open a review session for the GitHub pull request {number}. Without
    {number} the call takes the pull request of the current branch.

    {opts} accepts these fields: >lua

        {

                                                           *codeview.export()*
codeview.export({opts})
    Export the comments of the session that runs. {opts} accepts these
    fields: >lua

        {
          session = nil,   -- session to export, the active session by default
          register = nil,  -- register for the text, false writes no register
          buffer = true,   -- false skips the scratch buffer
          focus = true,    -- false keeps the cursor outside the buffer
          notify = true,   -- false silences the report of the call
          file = nil,      -- path of a file for the text, nil writes no file
        }
<
    The call returns `result, err`. The result holds the text, the number of
    comments, the register, the buffer, the window, and the file. See
    |codeview-export|.

    With `file`, the call writes the text to that file. The write is atomic:
    a reader sees the old file or the new file, never a part of a file. The
    call makes the missing directories. If the write fails, the call returns
    nil and the error.

                                                           *codeview.submit()*
codeview.submit({opts}, {cb})
    Send the comments of the session that runs to the pull request. The call
    shows a summary and posts only after the user confirms it.

    {opts} accepts these fields: >lua

        {
          session = nil,  -- session to submit, the active session by default
          event = nil,    -- "comment" | "approve" | "request-changes"
          body = nil,     -- text of the review, the prompt asks without it
          dir = nil,      -- directory that gh runs in, the repo root by default
          notify = true,  -- false silences the reports of the call
          ids = nil,      -- ids of the comments to send, every unsent comment by default
          confirm = true, -- false asks nothing and shows no summary
        }
<
    With `ids`, the call sends only these comments. An id that the session
    does not hold gives an error. A chosen comment that went out already
    does not go out again, and `result.already_sent` names it.

    With `confirm = false`, the call asks nothing: no event picker, no text
    prompt, and no summary. `event` is then required, and `body` is "" by
    default. The plugin posts only after the user confirms, in codeview or
    in the tool that calls it. |codeview-bridge| uses this form.

    {cb} gets `result, err`. The result holds the number of comments that
    GitHub took, the number of comments that stay local, the review of the
    answer, and its address. `result.existing` is true when GitHub held the
    review of an earlier try, so the call posted nothing.
    `result.stays_local` lists the comments that stay local, with the
    reason. See |codeview-submit| and |codeview-submit-guard|.

codeview.send({opts}, {cb})
    Send one comment to the pull request. The send key of the comment
    editor calls this function. >lua

        require("codeview").send({
          id = "0001",    -- id of the comment in the store
          session = nil,  -- session that holds the comment, the active session by default
          dir = nil,      -- directory that gh runs in, the repository root by default
          notify = true,  -- false silences the reports
        }, function(result, err) end)
<
    The result holds the same fields as |codeview.submit()|.

codeview.export_text({opts})
    Render the comments of the session as markdown. The call writes no
    register and opens no buffer. It returns `text, err`.

                                                           *codeview.health()*
codeview.health()
    Run the health check. |:checkhealth| codeview gives the same report.

                                                          *codeview.version*
codeview.version
    Version of the plugin, as text.

A session answers these calls: >lua

    session:label()          -- text of the range
    session:summary()        -- range, file count, and commit count
    session:changed_files()  -- list of changed files
    session:file(index)      -- one changed file
    session:counts()         -- file count and commit count, as text
    session:index_of(path)   -- position of a path in the list
    session:position_of(entry, index) -- position of an entry after a refresh
    session:refresh(opts, cb) -- resolve the range again and read the data
    session:reload(cb)       -- read a review of the working copy again
    session:on_close(fn)     -- call fn when the session closes
    session:off_close(fn)    -- drop a handler of on_close()
    session:close()          -- close the session
<
`session:refresh()` takes these options: >lua

    {
      snapshot = true,  -- false keeps the working copy out of the repository
      range = nil,      -- range that the caller resolved, to skip the resolve
    }
<
With `range`, the refresh reads that range and does not resolve the text of
the review a second time. The watcher passes the range of its check.

`session:position_of()` finds an entry of the file list after a refresh. The
path answers first. A commit document keeps its position, because a snapshot
of the working copy gives it a new path. The call returns nil when the range
does not hold the entry any more.

`session:close()` runs the close handlers from a copy of the list, so a
handler can call `session:off_close()` on another handler.

                                                      *codeview-close-confirm*
Set `close.confirm` to true to make the close key ask "Close the review?"
before it closes the session. The question comes from the close key of the
diff view and of the sidebar. An answer other than Yes keeps the session
open. `:Codeview close` and |codeview.close()| never ask. The close key of
the overview closes only the overview, so it does not ask either. After a
close, |:Codeview-reopen| opens the session again.

                                                        *codeview-backend*
The `backend` option selects the version control system. With "auto" the
plugin looks for a jj repository and for a git repository. It takes the
repository with the deepest root, so a git clone inside a jj repository keeps
the git backend. A colocated repository has a `.jj` directory and a `.git`
directory. Both roots are equal there, and the plugin takes the jj backend,
because the user drives such a repository with jj. Set the option to "git" or
to "jj" to force one backend. A forced backend needs its executable in $PATH.
Without the executable the plugin reports an error.

The jj backend reads the repository. Every jj call runs with
`--ignore-working-copy`, so a call does not snapshot the working copy. A file
that you changed after the last snapshot keeps its old content in the review.
One call is different: the reload of a review of `@` snapshots the working
copy first. See |codeview-edit-reload|. For a symbolic link the backend shows
the target of the link.

A revset that names no commit gives an error that says so, for example
`trunk()..@` on a workspace with no new commit. The virtual root commit of jj
holds no files, so the backend rejects it as a revision.

`--ignore-working-copy` also skips the import of the git refs, which jj does
at the start of a normal command. In a colocated repository a `git commit`
therefore stays invisible to the backend until the next import. The watcher
runs `jj git import` before each check, so the commit reaches the review. See
|codeview-auto-refresh|. `jj git import` does not import the git `HEAD`.

The git backend puts `--end-of-options` before every revision argument, so git
never reads a revision as an option. A revision that starts with `-` is not a
valid revision, and the backend reports a `bad_revision` error.

                                                  *codeview-backend-contract*
Both backends give the same answer for the same input. A plugin that calls
the backend of a session can rely on these rules:

- Text input goes to the revision language of the backend. git reads `a..b`
  as two revisions. jj reads it as a revset. The rules below apply to the
  table forms of a range.
- `kind = "single"` is one commit against its first parent.
- `kind = "range"` (`a..b`) is a diff of two trees. `from` is the base, and it
  is exclusive. The commits of the range are the ancestors of `to` that are
  not ancestors of `from`.
- `kind = "triple"` (`a...b`) takes the merge base of `from` and `to` as the
  base. Two sides with more than one merge base get one of them.
- A nil `from` is the state before the first commit. A commit without a
  parent gives a nil `from`. The jj backend never returns the id of its root
  commit, and a list of parents never holds it.
- Two histories without a common commit have no merge base. git then reports
  a `bad_revision` error. jj gives a nil `from`, because its root commit is
  common to all histories.
- The `revs` field of the log options names commits. The log lists them and
  all their ancestors, like `git log <rev>`.
- The `subject` of a commit is the first line of its message. The `body` is
  the rest, without the blank lines at its start and the white space at its
  end.

`lua/codeview/vcs/init.lua` holds the full interface of a backend.

                                                        *codeview-binaries*
Three options name the executables of the external tools: `git.binary` for
git, `jj.binary` for jj, and `github.binary` for gh. A plain name goes to
$PATH. An absolute path names the file itself. Use an option for a tool that
is not in $PATH, or for a wrapper of your own.

The value is one name, or one path. It is not a command line, so it holds no
argument: >lua

    require("codeview").setup({
      git = { binary = "/opt/homebrew/bin/git" },
      jj = { binary = "jj-wrapper" },
      github = { binary = "/opt/gh/bin/gh" },
    })
<
The plugin reads an option at the time of the call, so a later setup() call
changes the next command. `:checkhealth codeview` reports the name that you
set, and whether it finds the file. See |codeview-health|.

The comment editor also saves with `:w`. That write runs from an autocmd, not
from a map, so it works with any key of your own.

An entry takes one key, a list of keys, or false: >lua

    require("codeview").setup({
      keymaps = {
        show_comment = "gh",              -- one key
        comment_insert = { "i", "a" },    -- two keys for one action
        comment_visual = false,           -- no map for this action
      },
    })
<
A list of yours replaces the default list. It does not extend it.

The two word groups take no link. The plugin computes their colors from the
colorscheme, and so do |hl-CodeViewDiffAdd| and |hl-CodeViewDiffDelete| while
`diff.syntax` is on. To keep your own colors for these groups, set them from
your own |ColorScheme| autocmd, which runs after the one of the plugin.

The six box groups take no link either. |hl-CodeViewCommentBox| is 15
percent of the foreground of `DiagnosticInfo` on the background of `Normal`.
|hl-CodeViewRemoteBox| is 15 percent of the foreground of `Comment`.
|hl-CodeViewAgentBox| is 15 percent of the foreground of `DiagnosticHint`.
The box groups carry a background only, so the text of a box keeps the color
of |hl-CodeViewComment|, |hl-CodeViewRemote|, or |hl-CodeViewAgent|. The
border groups take the foreground of `FloatBorder` on the background of the
box. When `FloatBorder` has no foreground, or when its contrast with the box
is less than 3:1, the border takes the color of the tint. The frame then
stays visible on a dark box. When the colorscheme has no such colors, the box
groups link to `NormalFloat` and the border groups link to `FloatBorder`.

A transparent colorscheme gives `Normal` no background. The tint then goes on
the background of `NormalFloat`. When `NormalFloat` has no background too,
the tint goes on black for a dark 'background' and on white for a light one.
The box then has a color on the background of the terminal.

The inline comment editor takes |hl-CodeViewCommentBox| and
|hl-CodeViewCommentBorder| too, so a comment looks the same while you type it
and after you save it.

To give the boxes your own colors, set them from your own |ColorScheme|
autocmd: >lua

    vim.api.nvim_create_autocmd("ColorScheme", {
      callback = function()
        vim.api.nvim_set_hl(0, "CodeViewCommentBox", { bg = "#1d2b3a" })
        vim.api.nvim_set_hl(0, "CodeViewCommentBorder",
          { fg = "#5f87af", bg = "#1d2b3a" })
      end,
    })
<

To change a color, set the group after your colorscheme: >lua

    vim.api.nvim_set_hl(0, "CodeViewCurrent", { link = "Visual" })
<

17. HEALTH                                                     *codeview-health*

Run |:checkhealth| codeview. The report shows: >

    - the Neovim version, against the minimum version
    - the plugin version and the state of setup()
    - the result of the configuration validation
    - the git, jj, and gh executables with their versions
    - the login state of gh, from `gh auth status`
<
The login check asks GitHub whether the token is valid, so it needs a
connection. Without a login the report says how to get one.

The report names the executable of each option of |codeview-binaries|, and
it reads those options at the time of the check.
