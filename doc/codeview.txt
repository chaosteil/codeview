1. INTRODUCTION                                          *codeview-introduction*
                                                                    *codeview*

codeview shows the changes of a commit, or of a range of commits. You browse
the changed files in a sidebar, read the diffs inline or side by side, and
write comments on the lines. You export the comments as markdown, and you send
them to a GitHub pull request.

The plugin works on a git repository and on a jj repository, through one
backend interface. It writes no file of your repository: the comments of a
review live in one markdown file of their own. See |codeview-comments-store|.

Version 0.1.0. Start here: >vim

    :CodeView HEAD~3..HEAD
<
Then press <CR> on a file of the sidebar. |codeview-keymaps| holds every key.

==============================================================================
2. REQUIREMENTS                                          *codeview-requirements*

- Neovim 0.11 or later.
- git, for the git backend.
- jj, for the jj backend (optional).
- gh, for GitHub pull request review (optional).

==============================================================================
3. SETUP                                                        *codeview-setup*

The plugin works without a setup call. Every option then holds its default
value.

To change an option, call setup(): >lua

    require("codeview").setup({
      diff = { style = "split" },
    })
<
                                                          *codeview.setup()*
codeview.setup({opts})
    Merge {opts} into the defaults, validate the result, and store it.

    Return: ~
        The active configuration, or nil and a message when {opts} is invalid.

                                                          *codeview.config()*
codeview.config()
    Return the active configuration table.

                                                                  *g:codeview*
You can also set the variable `vim.g.codeview` before the plugin loads. The
plugin then calls setup() with that table: >lua

    vim.g.codeview = { sidebar = { position = "right" } }
<

4. COMMANDS                                                  *codeview-commands*

                                                                   *:CodeView*
:CodeView {rev}
    Review one commit. The base of the review is the parent of {rev}. For the
    first commit of the repository the base is the empty state.

    The command sends the argument to the backend as it is. A revision
    argument can hold spaces, for example `main@{2 days ago}`.

    Examples: >vim

        :CodeView HEAD
        :CodeView HEAD~3..HEAD
        :CodeView main...feature
<
:CodeView {rev}..{rev}
    Review the changes between the two revisions. The left side is the base.
    It is not part of the review.

:CodeView {rev}...{rev}
    Review the changes since the merge base of the two revisions.

:CodeView {revset}                                        *codeview-revsets*
    On a jj repository the argument is a revset. The command sends the text to
    jj as it is. The head of the revset is the new side of the review. The
    parent of the roots of the revset is the base.

    A revset that names more than one head is an error. Select one head.

    Examples: >vim

        :CodeView @
        :CodeView ::@
        :CodeView trunk()..@
<
                                                                *:CodeView-pr*
:CodeView pr [{number}]
    Review the GitHub pull request {number}. Without {number} the command
    takes the pull request of the current branch. The command needs the gh
    CLI. See |codeview-github|.

    Examples: >vim

        :CodeView pr 128
        :CodeView pr
<
:CodeView
    Open the commit picker. Select one commit to review it.

:CodeView!
    Open the picker in the range mode. Select the first commit of the range,
    then the last commit. Both commits are part of the review. The second list
    holds only the descendants of the first commit.

                                                        *codeview-subcommands*
The first word of the argument can also name a subcommand. A subcommand name
wins over a revision of the same name. To review a revision that a subcommand
names, write the revision as a range, for example `:CodeView close^..close`.

                                                             *:CodeView-close*
:CodeView close
    Close the review session. The command closes the windows and the buffers
    of the session.

                                                              *:CodeView-back*
:CodeView back
    Go back to the review from a file of the working copy. The window takes
    the diff of the file again, with the cursor on the row of the line that
    the file holds. See |codeview-edit-back|.

                                                             *:CodeView-files*
:CodeView files
    Open the changed-files sidebar and put the cursor in it. The command
    closes the sidebar when the sidebar is open.

                                                          *:CodeView-comments*
:CodeView comments
    Open the comment overview and put the cursor in it. The command closes the
    overview when the overview is open. See |codeview-overview|.

                                                            *:CodeView-export*
:CodeView export [{register}]
    Render the comments of the session as markdown. The text goes into a
    scratch buffer and into the register of the `export.register` option.
    {register} replaces the option for this call, for example
    `:CodeView export z`. See |codeview-export|.

:CodeView! export [{register}]
    Write the register only. The command opens no scratch buffer.

                                                            *:CodeView-submit*
:CodeView submit [{event}]
    Send the comments of the session to the pull request, as one review. The
    command shows a summary and posts only after you confirm it. {event} is
    `comment`, `approve`, or `request-changes`. Without {event} the command
    asks for it. See |codeview-submit|.

:CodeView! submit [{event}]
    Post with the default text of the review. The command asks no question
    about the text.

5. SESSIONS                                                  *codeview-sessions*

A session holds the backend handle, the resolved range, the commits of the
range, and the files that the range changes. The plugin keeps one session. A
second open closes the session that runs. A failed open keeps it.

The session sends these events: >

    User CodeViewSessionOpened      a session opened
    User CodeViewSessionRefreshed   a session read its data again
    User CodeViewSessionClosed      a session closed
<
The `data` field of the event holds plain values only: >

    data.id         number of the session
    data.spec       text that names the range
    data.files      number of changed files
    data.commits    number of commits in the range
<
Neovim copies the payload of a User event, so the payload cannot hold the
session object. To use the session methods, read the session with
|codeview.session()|: >lua

    vim.api.nvim_create_autocmd("User", {
      pattern = "CodeViewSessionOpened",
      callback = function(event)
        print(event.data.spec, require("codeview").session():summary())
      end,
    })
<
The close event comes after the session ended. |codeview.session()| gives nil
in that handler.

                                                     *codeview-commit-message*
The commits of the range come before the files. Every commit is one entry of
the sidebar, under a group node, and its name holds the short id and the
subject of the commit. The oldest commit reads first.

An entry opens like a file. The document of a commit holds:

    - the id, the author, and the date,
    - the message, with the subject and the body,
    - the files that the commit changes, with their status marks.

Comment on the document like on a line of code. The comment takes the commit
of the document, so every comment stays with its own commit.

A document is no file of the repository, and it has one side, so it stays in
the inline style. GitHub takes no comment on a commit message, so
|:CodeView-submit| keeps such a comment local and reports it in the summary.

Set `commit_message` to false to leave the commits out: >lua

    require("codeview").setup({ commit_message = false })
<

6. SIDEBAR                                                    *codeview-sidebar*

The sidebar shows the files that the range of the session changes, as a tree.
|:CodeView| opens it with the session, at the side that `sidebar.position`
names. Set `sidebar.auto_open` to false to open the sidebar with
|:CodeView-files| only. A session that starts from |codeview.open()| opens no
panel.

The first two lines are the header. The first line holds the range. The
second line holds the number of files and the number of commits. The tree
comes after an empty line: >

    9b2688a5..ec056be0
    4 files, 2 commits

      ▾ dir
      │   renamed.txt ← nested.txt R
    ▸   a.txt M
        added.txt A
        keep.txt D
<
The tree holds one node per directory and one node per file. A chain of
directories with one child each becomes one node, for example
`lua/codeview/vcs`. Directories come before files, and both come in
alphabetical order.

Each file line ends with a status mark: >

    A    the range adds the file
    M    the range changes the file
    D    the range deletes the file
    R    the range renames the file
    C    the range copies the file
    T    the range changes the type of the file
    U    the file is unmerged
    ?    the backend gave another status
<
A rename line and a copy line also show the old path, after an arrow. A
directory that hides its children shows the marks of the files below it.

The marker "▸" and the highlight group |hl-CodeViewCurrent| mark the file that
the diff view shows. The marker moves with every file that you open. A
directory that hides the marked file opens again.

                                                     *codeview-sidebar-keymaps*
The sidebar buffer holds these maps. |codeview-config| names the keys: >

    <CR>        open the file under the cursor, or toggle a directory
    <Tab>       toggle the directory of the line under the cursor
    zR          show the children of every directory
    zM          hide the children of every directory
    ]f          open the next file
    [f          open the previous file
    <leader>ct  switch the diff style
    <leader>co  open or close the comment overview
    q           close the review session
<
The next-file key and the previous-file key follow the order of the tree.
They step over the directory nodes, and they also reach a file in a directory
that hides its children.

The buffer of the diff view holds the maps `]f`, `[f`, and `q`. You walk
through the files without a move back to the sidebar. Each key press moves one
file, also while the backend still reads the file of the last press.

                                                       *codeview-sidebar-icons*
The tree uses text icons from `sidebar.icons`. The plugin needs no icon font
and no devicons plugin. For a terminal without support for the default
icons, set plain characters: >lua

    require("codeview").setup({
      sidebar = {
        icons = {
          expanded = "-",
          collapsed = "+",
          file = " ",
          guide = "|",
          current = ">",
        },
      },
    })
<

                                                            *codeview-layout*
The sidebar keeps its width. A file that opens takes the window of the file
that was open, so the tab page holds the same windows before and after. Only a
resize by hand changes the width of a panel, and a later open keeps that
width.

Neovim makes the windows of a tab page equal again after every open and every
close, when 'equalalways' is on. codeview holds that option off while it opens
or closes its own windows, and puts the width of every panel back afterwards.
Your own windows keep their behavior.

                                                   *codeview-sidebar-comments*
The first line of the sidebar is "Comments", with the number of comments of
the review. `<CR>` on that line opens the comment overview, and closes it
again. See |codeview-overview|.

                                                      *codeview-sidebar-mouse*
A double click acts like `<CR>`: it opens the file under the pointer, folds
the directory under the pointer, or opens the comment overview. The key comes
from the `open_file` option, so a list without `<2-LeftMouse>` takes the mouse
out. The 'mouse' option must hold the mode, which it does by default.

7. DIFF VIEW                                                     *codeview-diff*

The diff view shows one changed file in the main window. It reads both sides
of the file from the backend and compares them with |vim.diff()|. Two styles
show the result of that comparison:

    inline    one unified diff in one buffer
    split     two aligned buffers, the old side left, the new side right

The `diff.style` option names the style of the next file. |codeview-diff-style|
describes the switch between the two styles.

The buffers are read-only. Their filetype is `codeview-diff`. The buffer
variable `b:codeview_filetype` holds the filetype of the file itself: >

    @@ -1,6 +1,6 @@
     line 01
     line 02
    -line 03
    +line 03 changed
     line 04
     line 05
     line 06
    ⋯ 20 unchanged lines
    @@ -27,7 +27,7 @@
     line 27
<
In the inline style the first character of a line is the marker. A space marks
an unchanged line, `-` marks a removed line, and `+` marks an added line. The
status column shows the line number of the old file and the line number of the
new file.

A line that only one side holds shows one number. The plugin highlights a
removed line with |hl-CodeViewDiffDelete| and an added line with
|hl-CodeViewDiffAdd|. With `diff.word_diff` the changed part of a line also
gets |hl-CodeViewDiffText|.

                                                         *codeview-diff-syntax*
The diff keeps the colors of the code. A diff buffer holds two revisions with
a marker in front, so treesitter cannot attach to it. codeview parses each
side as a whole file instead, and writes the captures of the highlights query
into the rows of that side.

The diff colors then stay in the background: |hl-CodeViewDiffAdd| and
|hl-CodeViewDiffDelete| take the background of `DiffAdd` and `DiffDelete` and
carry no foreground, so the code keeps the colors of its language.

The layer needs a treesitter parser for the language of the file. A file
without one keeps the plain diff colors, and so does a binary file or a diff
above the line limit. Set `diff.syntax` to false to turn the layer off. The
row colors then take their foreground again: >lua

    require("codeview").setup({ diff = { syntax = false } })
<
                                                        *codeview-diff-context*
The view shows `diff.context` unchanged lines around each hunk. It hides a
longer unchanged section behind one filler row: >

    ⋯ 20 unchanged lines
<
A section that hides fewer than two lines stays open, because the filler row
costs as many screen rows as the lines that it hides.

Put the cursor on the row and press `za` to show the hidden lines. A second
press hides them again. `zR` shows every hidden line of the file, and `zM`
hides them all again. The hunk header keeps the line numbers of the collapsed
form, because the header names the position of the hunk in the file.

A file without a text diff shows one note instead of a diff: >

    The file has no changes.    a rename or a copy without a content change
    The file is empty.          both sides hold no line
    Binary file. It has no text diff.
<
                                                          *codeview-diff-limit*
The view reads the file of one row of the sidebar, and no other file. A range
of 400 files therefore opens as fast as a range of four.

A file can still be too large to compare. The `diff.max_lines` option holds the
highest number of lines that the two sides can hold together. Above that number
the view compares nothing and shows two rows: >

    The diff holds 48210 lines. The limit diff.max_lines is 20000.
    Press <CR> to show it.
<
The `load_diff` key reads the file again, without the limit. The key maps on
such a diff only, so `<CR>` keeps its own action in every other diff. The limit
applies to one file at a time, and the next file opens as usual. Set
`diff.max_lines` to 0 to remove the limit for every file.

|:CodeView-submit| never sees the limit. It maps the position of a comment on
the full diff of the file, whether the view rendered that diff or not.

                                                          *codeview-diff-split*
The side-by-side style shows the old version at the left and the new version
at the right: >

    @@ -1,4 @@              @@ +1,6 @@
    one                     one
    two                     two changed
    three                   three
    four                    four
                            five
                            six
<
Both sides hold the same number of rows, so a change sits on the same screen
row in both windows. A change that adds more lines than it removes gets a
filler row at the left, and a change that removes more lines than it adds gets
a filler row at the right. A filler row holds no text. It shows the highlight
|hl-CodeViewDiffFiller| and virtual text, so it never reads as a line of the
file.

The two windows scroll and move the cursor together, through 'scrollbind' and
'cursorbind'. The status column of the left window shows the line numbers of
the old file, and the status column of the right window the numbers of the new
file. Both styles hide the same unchanged sections, and `za`, `zR`, and `zM`
work in both.

The two windows show one diff together. If you close one of them, the view
takes the inline style in the window that stays. The `diff.style` option keeps
its value, so the next file opens side by side again.

                                                          *codeview-diff-style*
Press `<leader>ct` in the diff view or in the sidebar to switch the style. The
switch keeps the diff, so the backend reads no file again, and it keeps the
cursor on the same line of the file. A cursor on a removed line moves to the
left window. A cursor on a hunk header, or on the row of a collapsed section,
stays on that header or on that row. The new style also becomes the
`diff.style` option, so the next file opens in the same style.

To start every review in the side-by-side style, set the option: >lua

    require("codeview").setup({ diff = { style = "split" } })
<
                                                        *codeview-diff-keymaps*
The diff buffer holds these maps. |codeview-config| names the keys: >

    ]h          jump to the next hunk
    [h          jump to the previous hunk
    za          show or hide the section under the cursor
    zR          show every hidden line
    zM          hide every section again
    ]f          open the next file
    [f          open the previous file
    <CR>        render a diff above the `diff.max_lines` limit, on such a diff
    <leader>ct  switch the diff style
    i a o O     comment on the line under the cursor
    I A c       comment on the selected lines, in the visual mode
    <leader>cc  comment on the line or on the selection
    <leader>ce  edit the comment under the cursor
    <leader>cd  delete the comment under the cursor
    <leader>cr  resolve the comment, or open it again
    <leader>co  open or close the comment overview
    K           show the comment under the cursor in a float
    q           close the review session
<
|codeview-keymaps| holds the full list, with the option name of each key.

The diff view sends one event: >

    User CodeViewFileOpened    a file opened in the view
<
The `data` field of the event holds these values: >

    data.session    number of the session
    data.index      position of the file in the file list
    data.path       path of the file
    data.status     status of the file in the range
    data.style      style of the render, "inline" or "split"
    data.buf        buffer that holds the diff
<
The event also comes after a change of the style, because the buffer of the
file is a new buffer then.

                                                        *codeview-diff-linemap*
The view keeps a line map. The map holds one record per buffer row, with the
kind of the row, the line in the old file, the line in the new file, and the
hunk of the row. Read the map with |codeview.view()|: >lua

    local map = require("codeview").view().map
    local row = vim.api.nvim_win_get_cursor(0)[1]
    print(map:kind(row), map:file_line(row))   -- "add", 12, "new"
    print(map:buf_row(12, "new"))              -- 5
<
                                                              *codeview-edit*
`gf` leaves the review and edits the real file. The window of the diff takes
the file of the working copy, with the cursor on the line that the diff shows.
The buffer is a normal file buffer, so `:w` writes it.

The working copy is not the revision of the review. The line is therefore the
line of the change, and the text around it can differ. A row of the old side
has no line of its own, so the nearest row of the new side answers for it.

The sidebar stays open, and `<CR>` on the file reads its diff again. The
window of the file leaves the session, so |:CodeView-close| keeps it open.

The key also works on a file line of the sidebar. It reports a commit document
and a file that the working copy does not hold, for example a file that the
range deletes.

                                                         *codeview-edit-back*
`<leader>cb` goes back. The window takes the diff of the file again, with the
cursor on the row of the line that you left. |:CodeView-back| does the same
from any window.

The key sits on the file that the edit key opened, and on no other buffer. It
is the way back, because the jump list of Neovim holds no entry for the diff:
the diff buffer wipes itself when the window leaves it.

A file with changes that are not written needs 'hidden', or a write first,
because the window cannot leave a modified buffer otherwise.

8. COMMENTS                                                  *codeview-comments*

A comment holds a file, a line range, a side of the diff, a commit, and a
markdown body. The plugin keeps every comment of a session in one file. A
reopen of the same range shows the comments again.

The diff buffer stays read-only. A comment never becomes a line of the buffer.
The view shows a comment with extmarks only: a sign on every covered row, and
virtual lines below the range. The line count of the diff buffer never
changes, so the line map of the render stays correct.

                                                     *codeview-comments-keys*
The insert keys write comments. They do nothing in a read-only buffer, so the
diff buffer maps them to the comment editor: >

    i a         edit the comment of the line, or write the first one
    o O         write another comment on the line
    I A c       comment on the selected lines, in the visual mode
    <leader>cc  edit or write the comment of the line, or of the selection
    <leader>ce  edit the comment under the cursor
    <leader>cd  delete the comment under the cursor, after a question
    <leader>cr  resolve the comment under the cursor, or open it again
    <leader>co  open or close the comment overview
    K           show the comment under the cursor in a float
<
`i` and `a` read the line first. A line that already holds a comment opens
that comment in the editor, the way `i` changes the text that a normal buffer
holds. A line without a comment starts a new one. `o` and `O` always start a
new comment, so a second comment on the same line stays one keypress away. A
line with more than one comment asks which comment to edit.

While the editor holds a comment, the diff drops the virtual lines of that
comment and keeps its sign, because the editor shows the same text one row
below the sign.

The visual mode keeps `i` free, because `i` is the prefix of the text objects.
`vi(` still selects a text object in the diff buffer. The maps are
buffer-local. They never reach a file buffer of your own.

Every key comes from the `keymaps` option. Set an entry to false to disable
it, or give a list of keys for one action: >lua

    require("codeview").setup({
      keymaps = {
        comment_insert = { "i", "a" },   -- fewer insert keys
        comment_visual = false,          -- no visual mode maps
        show_comment = "gh",
      },
    })
<
                                                   *codeview-comments-editor*
The editor is a floating window with its own markdown buffer. This buffer is
the only modifiable buffer of the comment flow. You never type into the diff
buffer, and the plugin never writes to a file of the repository.

In the editor: >

    :w          save the comment
    ZZ          save the comment
    q           discard the comment
    <Esc><Esc>  discard the comment
<
An empty body counts as a discard. A close of the window discards the comment
too. The `editor_save` option and the `editor_cancel` option name the two keys.
The `:w` write runs from an autocmd, so it saves with any key of your own.

                                                    *codeview-comments-anchor*
The anchor of a comment comes from the line map of the render. The cursor row
gives the file line and the side:

    - A removed line anchors to the old side.
    - An added line anchors to the new side.
    - An unchanged line anchors to the new side, like the GitHub review UI.

In the side-by-side style the window under the cursor selects the side. The
left window comments on the old file, and the right window on the new file. A
comment keeps its anchor across a change of the style, because both styles
read the same file lines.

A comment on a line of a collapsed section moves its sign to the row above the
section. A section at the start of the file has no row above it, so the sign
goes on the row of the section itself. The row of the sign also answers for
the edit key and for the delete key. Press `za` to show the lines again.

                                                    *codeview-comments-editor*
The `comments.editor` option selects where the editor opens: >

    inline    under the commented row, in the width of the diff (default)
    float     in the middle of the screen, with a border
<
The inline editor opens the diff at the commented row. The space comes from
virtual lines, so the diff keeps its rows, keeps its line map, and stays
read-only. The lines under the comment move down while you type, and they move
back when you save or discard. A window that shows no diff row, for example an
edit from the comment overview, opens the float instead.

The editor starts in insert mode, after the last character of the text. Set
`comments.start_insert` to false to start in normal mode.

                                                   *codeview-comments-display*
The `comments.display` option selects the display: >

    virtual   the body shows in virtual lines below the range (default)
    float     the row keeps the sign only
<
The `K` key shows the comment in a float in both cases.

                                                     *codeview-comments-state*
A comment holds a state: "open" or "resolved". The resolve key changes the
state, and the state goes into the `state` field of the comment, so it
survives a restart. A resolved comment takes the sign of the
`comments.resolved_sign` option, and its header line says "resolved". Use the
comment overview to walk the open comments of the review. See
|codeview-overview|.

In the side-by-side style a comment keeps the two windows aligned. The other
side takes virtual lines of the same number, without text, so both windows
grow by the same height. The sign column of a split window has a fixed width,
so a sign on one side does not move the text of that side alone.

                                                     *codeview-comments-store*
The comments of one session live in one markdown file. The directory comes
from the `comments.dir` option and from the path of the repository. The file
name is a hash of the repository root and of the resolved range, so a reopen
of the same range finds the file again: >

    ~/.local/share/nvim/codeview/review/<repo-slug>-<hash>/<session-key>.md
<
The frontmatter of the file holds the session data. Each comment is one
section with a field block and a markdown body: >

    ---
    version: 1
    key: 4f1c0a2b8d3e5f60
    repo: /home/ada/code/demo
    range: aaaa1111..bbbb2222
    spec: main..@
    created_at: 2026-08-12T09:00:00Z
    updated_at: 2026-08-12T09:30:00Z
    ---

    # codeview review: main..@

    ## codeview-comment 68a1c2f30b7a

    - file: lua/codeview/store.lua
    - start_line: 12
    - end_line: 14
    - side: new
    - commit: bbbb2222
    - state: open
    - synced_at:
    - review_id:
    - created_at: 2026-08-12T09:10:00Z
    - updated_at: 2026-08-12T09:10:00Z

    The body of the comment.
<
The fields hold: >

    file          path of the file in the new revision
    start_line    first line of the comment, in the file at `commit`
    end_line      last line of the comment
    side          "old" for a removed line, "new" for every other line
    commit        revision that the lines come from
    state         "open" or "resolved"
    synced_at     time of the submit that sent the comment to GitHub
    review_id     review of GitHub that holds the comment
    created_at    time of the first save
    updated_at    time of the last change
<
The two sync fields stay empty until a |:CodeView-submit| confirms the post.
See |codeview-submit-state|.

The plugin writes the file atomically. It writes a temporary file in the same
directory and renames it over the target. A failed write keeps the file of the
last save.

Read the store from Lua with |codeview.store()|.

                                                             *codeview-hints*
A row at the bottom of the screen shows the keys of the window that has the
cursor, the way a terminal tool does: >

     ]h next hunk  ]f next file  za unfold  <space>ct style  K read comment
<
The row holds the keys that a reader does not guess from the window. `i`
writes a comment and `<CR>` opens the file under the cursor, so neither reads
in the row. The style toggle does read there, because nothing else names it.

The row is a window of one line, and not a float, so it covers no line of a
diff and no statusline. It opens with the session and closes with it. It
follows the `keymaps` option, so it names the keys that you set.

Set `hints.enabled` to false to leave the row out. Set `hints.actions` to name
the actions of one surface yourself. The surfaces are "sidebar", "view", and
"overview": >lua

    require("codeview").setup({
      hints = {
        actions = {
          view = {
            { action = "toggle_style", text = "style" },
            { action = "toggle_overview", text = "comments" },
          },
        },
      },
    })
<

9. COMMENT OVERVIEW                                          *codeview-overview*

The comment overview lists every comment of the session in one panel. Open it
with |:CodeView-comments|, or with `<leader>co` from the sidebar and from the
diff. Set `overview.auto_open` to true to open it with every |:CodeView|.

The overview groups the comments in the same tree as the changed-files
sidebar. A comment is a child of its file. Every node shows the number of
comments below it: >

    9b2688a5..ec056be0
    3 comments, 1 resolved

      ▾ lua/codeview 1
      │ ▾ store.lua 1
      │ │ ✓ L5 new 4f1c0a2 rename this function
      ▾ call.lua 2
      │ ▌ L1 new 4f1c0a2 the first note
      │ ▌ L2-3 old 4f1c0a2 two lines
<
One comment line holds the sign of the state, the line range, the side, the
short commit, and the first line of the body. A body that is wider than the
panel ends with an ellipsis. The sign comes from the `comments.sign` option
for an open comment, and from the `comments.resolved_sign` option for a
resolved comment.

                                                    *codeview-overview-keymaps*
The overview buffer holds these maps. |codeview-config| names the keys: >

    <CR>        open the comment in the diff, or toggle a directory
    <Tab>       show or hide the comments of the file under the cursor
    zR          show the comments of every file
    zM          hide the children of every node
    <leader>ce  edit the comment under the cursor
    <leader>cd  delete the comment under the cursor, after a question
    <leader>cr  resolve the comment under the cursor, or open it again
    <leader>co  close the overview
    q           close the overview
<
`q` closes the overview only. The session stays open, and the changed-files
sidebar stays open.

                                                      *codeview-overview-jump*
`<CR>` on a comment opens the diff of its file and moves the cursor to the
anchor of the comment. A collapsed section that hides the line shows its lines
again. In the side-by-side style the cursor goes to the window of the side of
the comment. `<CR>` on a file line opens the first comment of the file.

A file that the range does not change any more keeps its comments, but the
jump key cannot open it. The overview shows the name of such a file dim.

                                                    *codeview-overview-events*
Every change of a comment sends an event. The overview and the diff view
subscribe to it, so a delete in the overview clears the extmarks of the diff
at once, and a comment in the diff shows in the overview at once. Each event
also runs a |User| autocmd: >

    CodeViewCommentAdded      a new comment went into the store
    CodeViewCommentChanged    the body or the state of a comment changed
    CodeViewCommentDeleted    a comment left the store
    CodeViewReviewSubmitted   a submit sent comments to GitHub
<
The payload holds the id of the comment, the file, the id of the session, and
the state: >lua

    vim.api.nvim_create_autocmd("User", {
      pattern = "CodeViewCommentAdded",
      callback = function(event)
        vim.print(event.data.file, event.data.id)
      end,
    })
<

10. EXPORT                                                     *codeview-export*

The export renders the comments of the session as markdown. Run
|:CodeView-export|. The text goes into a scratch buffer and into a register,
so you paste the review into a chat window or into a pull request description.

The default template is plain markdown: >markdown

    # codeview review: main..@

    - range: `9b2688a5..ec056be0`
    - commits: 2
    - comments: 3 on 2 files, 1 resolved

    ## call.lua

    ### L1 · new · ec056be0

    the first note

    ### L2-3 · old · 9b2688a5 · resolved

    two lines
<
Each comment holds its line range, its side, and the commit of the lines. A
reader finds the code with those three values, without the plugin. `L1` is the
line in the file at that commit. The side is "new" for an added line or for an
unchanged line, and "old" for a removed line. A resolved comment holds the word
"resolved" in its header.

The files come in the order of the changed-files sidebar, and the comments of
one file come in line order. A file with comments that the range does not
change any more comes last, with the note "(outside the range)".

`q` closes the window of the export buffer. A second export of the same session
replaces the buffer of the first one. |:CodeView-close| closes the export
window with the other windows of the session.

                                                     *codeview-export-register*
The `export.register` option names the register. The default is "+", the
system clipboard. Set the option to another name to keep the clipboard free:
>lua

    require("codeview").setup({ export = { register = "z" } })
<
An argument of the command wins over the option. An empty option writes no
register. The name must be one register character. A longer text writes no
register and gives a warning. "+" and "*" need a clipboard tool. Without one
the export writes no register and gives a warning. See |clipboard|.

                                                     *codeview-export-template*
The `export.template` option replaces the default template. The function gets
the session and the data of the export, and returns the text: >lua

    require("codeview").setup({
      export = {
        template = function(session, data)
          local lines = { "# " .. session:label() }
          for _, comment in ipairs(data.comments) do
            local at = comment.file .. ":" .. comment.start_line
            lines[#lines + 1] = at .. " " .. comment.body
          end
          return table.concat(lines, "\n")
        end,
      },
    })
<
The data table holds these fields: >lua

    data.session    -- session of the export
    data.store      -- comment store of the session
    data.spec       -- text that names the range
    data.range      -- resolved range, with short revision ids
    data.repo       -- absolute path of the repository root
    data.files      -- files with comments, each with its comment list
    data.comments   -- every comment, in the order of the render
    data.count      -- number of comments
    data.resolved   -- number of resolved comments
<
A template that fails, or that gives a value that is not a text, falls back to
the default template. The plugin reports the problem.

11. PULL REQUESTS                                              *codeview-github*

`:CodeView pr {number}` reviews a pull request of GitHub. The review reads and
writes nothing on GitHub: it holds your comments in the session file, like a
local review. |:CodeView-export| gives you the text for the web page.

The command needs the gh CLI in $PATH, and a login. Run `gh auth login` once.
`:checkhealth codeview` reports both. See |codeview-health|.

                                                        *codeview-github-refs*
The working copy does not change. The command fetches two refs of the plugin
and checks out no branch: >

    refs/codeview/pr/{number}/head    the commits of the pull request
    refs/codeview/pr/{number}/base    the tip of the base branch
<
The review range is `base...head`, so it starts at the merge base of the two
refs. That is the range of the "Files changed" tab of GitHub. The sidebar
header shows the number and the title of the pull request.

A pull request review needs a git repository. A colocated jj repository holds
one, so it works there too.

The `github.remote` option names the git remote of the fetch. An empty text
takes `origin`, or the first remote of the repository.

                                                       *codeview-github-store*
The session key of the comment file is `pr-{number}-{head commit}`. A new push
to the pull request gives a new head commit, so the next review starts with an
empty comment file and your notes on the older push stay where they are. See
|codeview-comments-store|.

                                                     *codeview-github-remote*
The review comments of the pull request come in after the session opens. The
diff shows them under their line, with the sign of the `comments.remote_sign`
option, the login of the author, and the word "read-only". The comment
overview lists them in a section of their own, under the local comments.

A remote comment is read-only. The edit key, the delete key, and the resolve
key report that and change nothing. `<CR>` on a remote comment opens its line
in the diff, like a local comment.

GitHub reports the position of a comment in three ways, and the mapping takes
the first one that answers: the lines of the newest version of the diff, the
lines of the version that the comment was written on, and the last line of the
diff hunk. A comment that a later push moved shows the word "outdated".

A comment that a submit of this session sent lives on GitHub and in the
session file. The review drops the copy of GitHub and keeps the local comment
with the word "synced", so the comment shows once.

Set `github.comments` to false to leave the review comments out. The option
`github.max_comments` limits the number of comments of one fetch.

A failed fetch of the comments gives one message. The review itself stays
open, because it needs no network after the fetch of the refs.

|:CodeView-submit| sends your comments to the pull request. See
|codeview-submit|.

==============================================================================
12. SUBMIT                                                     *codeview-submit*

|:CodeView-submit| sends the comments of the session to the pull request. The
comments go out as one review. The pull request then shows one entry with all
the lines.

The command needs a session of |:CodeView-pr|. A local review has no pull
request, so the command reports that and stops.

The post is always explicit: >

    1. The command collects the comments that no submit sent yet.
    2. It asks for the event of the review.
    3. It asks for the text of the review.
    4. It shows the summary: every comment that goes out, and every comment
       that stays local.
    5. It posts after you pick "submit".
<
Nothing reaches GitHub before that pick. No autocommand, no write of a file,
and no keymap posts by itself.

`:CodeView submit {event}` skips the question about the event. The events are: >

    comment           the review adds comments only
    approve           the review approves the pull request
    request-changes   the review asks for changes
<
`:CodeView! submit` skips the question about the text of the review. GitHub
needs a text for the comment event and for the request-changes event, so the
review then holds one default line.

                                                    *codeview-submit-position*
The position of a comment comes from a line map of the diff. The map runs with
the diff settings of git, the myers algorithm with the indent heuristic,
because GitHub takes only the lines of the diff of git. The review itself
shows the histogram diff, which reads better. The map gives the fields of the
review API of GitHub: >

    side          LEFT for the old side, RIGHT for the new side
    line          last line of the comment
    start_line    first line of a comment over more than one line
    start_side    side of the first line
<
GitHub takes a comment only on a line of its diff. A comment on another line
stays local. The summary names that comment with the reason. These comments do
not map: >

    - the pull request does not change the file any more
    - the diff of the pull request does not hold the line
    - the line range of the comment is not one block of the diff
<
Move such a comment to a line of the diff, or read it with |:CodeView-export|.

The diff of GitHub keeps three unchanged lines around each change. The review
buffer can show one line more, because it hides no section of one line. A
comment on such a line stays local, and the summary names it. The submit
reports the line before the post. It does not send a line that GitHub rejects.

                                                       *codeview-submit-state*
A comment carries its sync state in the session file: >

    - synced_at: 2026-08-13T09:41:12Z
    - review_id: 2371558991
<
A comment gets both fields only after GitHub confirms the post. The next
submit then leaves this comment out, so no comment goes out twice. The diff
and the comment overview show the word "synced" on it.

An edit of the text clears the sync state. The pull request holds the text of
the last submit, so the next submit sends the new text. GitHub takes it as a
new comment, because the review API writes no comment a second time.

A failed post writes nothing. No comment gets the fields, and the session file
does not change. The report holds the answer of the server, for example the
line that GitHub did not take. Correct the comment, then run the command
again.

A submit sends the event CodeViewReviewSubmitted. See
|codeview-overview-events|.

13. LUA API                                                       *codeview-api*

                                                             *codeview.open()*
codeview.open({spec}, {opts}, {cb})
    Open a review session for {spec}. {spec} is revision text such as "HEAD"
    or "main..feature", or a table with resolved revisions.

    {opts} accepts these fields: >lua

        {
          repo = nil,     -- repository handle, to skip the detection
          dir = nil,      -- directory for the detection, cwd by default
          backend = nil,  -- "auto" | "git" | "jj", the config value by default
        }
<
    Without {cb} the call blocks and returns `session, err`. With {cb} the
    call returns at once and calls `cb(session, err)`.

                                                          *codeview.open_pr()*
codeview.open_pr({number}, {opts}, {cb})
    Open a review session for the GitHub pull request {number}. Without
    {number} the call takes the pull request of the current branch.

    {opts} accepts these fields: >lua

        {
          dir = nil,       -- directory for the detection, cwd by default
          repo = nil,      -- "owner/name" of another repository
          remote = nil,    -- git remote, the config value by default
          comments = true, -- read the review comments of the pull request
        }
<
    Without {cb} the call blocks and returns `session, err`. With {cb} the
    call returns at once and calls `cb(session, err)`.

                                                                *codeview.pr()*
codeview.pr()
    Return the pull request of the session that runs, or nil. The table holds
    the number, the title, the state, the author, the branches, the commits,
    and the head commit.

                                                   *codeview.remote_comments()*
codeview.remote_comments()
    Return the review comments that the pull request of the session already
    holds. Each comment has a file, a line range, a side, an author, a body,
    and an `outdated` field. The list is empty for a local review.

                                                             *codeview.pick()*
codeview.pick({opts}, {cb})
    Open the commit picker. Set `opts.mode` to "range" to ask for two picks.
    The callback gets nil and nil when the user cancels the picker.

                                                          *codeview.session()*
codeview.session()
    Return the session that runs, or nil.

                                                            *codeview.close()*
codeview.close()
    Close the session that runs. Return false when no session runs.

                                                          *codeview.sidebar()*
codeview.sidebar()
    Return the sidebar that runs, or nil.

                                                     *codeview.open_sidebar()*
codeview.open_sidebar({opts})
    Open the changed-files sidebar for the session that runs. {opts} accepts
    a `session` field and a `focus` field. The call returns `sidebar, err`.

                                                    *codeview.close_sidebar()*
codeview.close_sidebar()
    Close the sidebar. The session stays open. Return false when no sidebar
    is open.

                                                   *codeview.toggle_sidebar()*
codeview.toggle_sidebar({opts})
    Close the sidebar when it is open, and open it when it is closed. Return
    the state after the call.

                                                         *codeview.overview()*
codeview.overview()
    Return the comment overview that runs, or nil.

                                                    *codeview.open_overview()*
codeview.open_overview({opts})
    Open the comment overview for the session that runs. {opts} accepts a
    `session` field and a `focus` field. The call returns `overview, err`.

    The overview answers these calls: >lua

        overview:comments()        -- comments in the order of the render
        overview:cursor_comment()  -- comment of the line under the cursor
        overview:jump(comment)     -- open the anchor of a comment in the diff
        overview:go_to(id)         -- move the cursor to the line of a comment
        overview:edit()            -- edit the comment under the cursor
        overview:remove(opts)      -- delete the comment under the cursor
        overview:set_state(state)  -- resolve the comment, or open it again
        overview:render()          -- render the panel again
        overview:close()           -- close the panel
<
                                                   *codeview.close_overview()*
codeview.close_overview()
    Close the comment overview. The session stays open. Return false when no
    overview is open.

                                                  *codeview.toggle_overview()*
codeview.toggle_overview({opts})
    Close the overview when it is open, and open it when it is closed. Return
    the state after the call.

                                                             *codeview.view()*
codeview.view()
    Return the state of the diff view, or nil when no file is open. The state
    holds the path, the status, the diff, the style, the line map, the buffer,
    and the window. In the side-by-side style it also holds the buffer, the
    window, and the line map of the old side: `old_buf`, `old_win`, and
    `old_map`.

                                                        *codeview.open_file()*
codeview.open_file({index}, {opts}, {cb})
    Open one changed file of the session in the diff view. {index} is the
    position of the file in the file list. {opts} accepts a `session` field and
    a `force` field. With `force = true` the call renders a diff above the
    `diff.max_lines` limit. See |codeview-diff-limit|.

                                                        *codeview.load_diff()*
codeview.load_diff({cb})
    Render the diff that the `diff.max_lines` limit stopped. The call reads the
    file of the view again, without the limit. It returns false when the view
    shows no limited diff.

                                                        *codeview.next_hunk()*
codeview.next_hunk({opts})
    Move the cursor to the first row of the next hunk. Set `opts.wrap` to true
    to continue at the first hunk. Return the row, or nil.

                                                        *codeview.prev_hunk()*
codeview.prev_hunk({opts})
    Move the cursor to the first row of the previous hunk. Set `opts.wrap` to
    true to continue at the last hunk. Return the row, or nil.

                                                            *codeview.style()*
codeview.style()
    Return the style of the diff view, or the style of the next file.

                                                        *codeview.set_style()*
codeview.set_style({style})
    Set the diff style to "inline" or "split". Without {style} the call takes
    the other style. The call returns the style after it, or nil for an
    unknown name.

                                                     *codeview.toggle_style()*
codeview.toggle_style()
    Switch between the inline style and the side-by-side style.

                                                        *codeview.edit_file()*
codeview.edit_file({opts})
    Leave the review and edit the file of the working copy. {opts} takes
    `path`, `line`, and `win`. Without them the call reads the file and the
    line of the diff that is open. See |codeview-edit|.

    Return: ~
        True when a file opened.

                                                   *codeview.toggle_context()*
codeview.toggle_context({id}, {expanded})
    Show or hide the lines of a collapsed section. Without {id} the call acts
    on the section under the cursor. Return false without a section.

                                                          *codeview.comment()*
codeview.comment({opts})
    Open the comment editor for the line under the cursor. With
    `opts.visual = true` the comment covers the lines of the selection.
    `opts.first` and `opts.last` name buffer rows of the diff.

    Return false when the row holds no line of the file.

                                                     *codeview.edit_comment()*
codeview.edit_comment({opts})
    Open the editor for the comment under the cursor. `opts.id` names another
    comment. Return false without a comment.

                                                   *codeview.delete_comment()*
codeview.delete_comment({opts})
    Delete the comment under the cursor, after a question. `opts.confirm =
    false` skips the question. `opts.id` names another comment.

                                                  *codeview.resolve_comment()*
codeview.resolve_comment({opts})
    Set the state of the comment under the cursor. `opts.state` is "open" or
    "resolved". Without a state the call takes the other state. `opts.id`
    names another comment. Return the comment after the change.

                                                     *codeview.show_comment()*
codeview.show_comment()
    Show the comment under the cursor in a float. Return the buffer and the
    window of the float.

                                                         *codeview.comments()*
codeview.comments()
    List of the comments of the session that runs.

                                                            *codeview.store()*
codeview.store()
    Comment store of the session that runs, or nil and an error. The store
    answers these calls: >lua

        store.path                    -- path of the session file
        store.key                     -- session key
        store:count()                 -- number of comments
        store:get(id)                 -- one comment
        store:for_file(path, opts)    -- comments of one file
        store:at(path, side, line)    -- comments that cover one line
        store:add(fields)             -- add a comment
        store:update(id, fields)      -- change a comment
        store:remove(id)              -- delete a comment
        store:unsynced()              -- comments that no submit sent yet
        store:mark_synced(id, opts)   -- mark a comment as sent
        store:save()                  -- write the file

                                                           *codeview.export()*
codeview.export({opts})
    Export the comments of the session that runs. {opts} accepts these
    fields: >lua

        {
          session = nil,   -- session to export, the active session by default
          register = nil,  -- register for the text, false writes no register
          buffer = true,   -- false skips the scratch buffer
          focus = true,    -- false keeps the cursor outside the buffer
          notify = true,   -- false silences the report of the call
        }
<
    The call returns `result, err`. The result holds the text, the number of
    comments, the register, the buffer, and the window. See |codeview-export|.

                                                           *codeview.submit()*
codeview.submit({opts}, {cb})
    Send the comments of the session that runs to the pull request. The call
    shows a summary and posts only after the user confirms it.

    {opts} accepts these fields: >lua

        {
          session = nil,  -- session to submit, the active session by default
          event = nil,    -- "comment" | "approve" | "request-changes"
          body = nil,     -- text of the review, the prompt asks without it
          dir = nil,      -- directory that gh runs in, the repo root by default
          notify = true,  -- false silences the reports of the call
        }
<
    {cb} gets `result, err`. The result holds the number of comments that
    GitHub took, the number of comments that stay local, the review of the
    answer, and its address. See |codeview-submit|.

                                                      *codeview.export_text()*
codeview.export_text({opts})
    Render the comments of the session as markdown. The call writes no
    register and opens no buffer. It returns `text, err`.

                                                           *codeview.health()*
codeview.health()
    Run the health check. |:checkhealth| codeview gives the same report.

                                                          *codeview.version*
codeview.version
    Version of the plugin, as text.

A session answers these calls: >lua

    session:label()          -- text of the range
    session:summary()        -- range, file count, and commit count
    session:changed_files()  -- list of changed files
    session:file(index)      -- one changed file
    session:index_of(path)   -- position of a path in the list
    session:refresh(cb)      -- read the files and the commits again
    session:close()          -- close the session

14. CONFIGURATION                                              *codeview-config*

Defaults: >lua

    {
      backend = "auto",              -- "auto" | "git" | "jj"
      commit_message = true,         -- the commit message as the first file
      diff = {
        style = "inline",            -- "inline" | "split"
        context = 3,                 -- unchanged lines around a hunk
        max_lines = 20000,           -- lines of both sides, 0 removes the limit
        word_diff = true,            -- highlight changed words
        syntax = true,               -- colors of the language of the file
      },
      sidebar = {
        position = "left",           -- "left" | "right"
        width = 20,
        auto_open = true,
        icons = {
          expanded = "▾",            -- directory that shows its children
          collapsed = "▸",           -- directory that hides its children
          file = " ",                -- file, to keep the names in one column
          guide = "│",               -- indent guide of one tree level
          current = "▸",             -- file that the diff view shows
        },
      },
      overview = {
        position = "right",          -- "left" | "right"
        width = 48,
        auto_open = false,           -- open the overview with the session
      },
      comments = {
        dir = stdpath("data") .. "/codeview/review",
        display = "virtual",         -- "virtual" | "float"
        sign = "▌",                  -- sign of a commented line
        resolved_sign = "✓",         -- sign of a resolved comment
        remote_sign = "▏",           -- sign of a comment from GitHub
        border = "rounded",          -- border of the editor and of the float
        width = 72,                  -- width of the editor, in columns
        height = 10,                 -- height of the editor, in lines
        editor = "inline",           -- "inline" | "float"
        start_insert = true,         -- start the editor in insert mode
      },
      hints = {
        enabled = true,             -- key row at the bottom of the screen
        actions = false,            -- false takes the built-in lists
      },
      export = {
        register = "+",
        template = false,            -- false uses the built-in renderer
      },
      github = {
        remote = "",                 -- git remote, "" takes origin
        comments = true,             -- read the review comments of the PR
        max_comments = 500,          -- highest number of comments of a fetch
      },
      keymaps = {
        open_file = { "<CR>", "<2-LeftMouse>" },
        toggle_node = "<Tab>",
        expand_all = "zR",
        collapse_all = "zM",
        next_file = "]f",
        prev_file = "[f",
        next_hunk = "]h",
        prev_hunk = "[h",
        expand_context = "za",
        load_diff = "<CR>",
        toggle_style = "<leader>ct",
        edit_file = "gf",
        back = "<leader>cb",
        comment = "<leader>cc",
        comment_insert = { "i", "a" },
        comment_add = { "o", "O" },
        comment_visual = { "I", "A", "c" },
        edit_comment = "<leader>ce",
        delete_comment = "<leader>cd",
        resolve_comment = "<leader>cr",
        show_comment = "K",
        toggle_overview = "<leader>co",
        editor_save = "ZZ",
        editor_cancel = { "q", "<Esc><Esc>" },
        close = "q",
      },
      log_level = vim.log.levels.WARN,
    }

Set a keymap to false to disable it. A list holds more than one key for one
action, and a list from you replaces the default list. setup() rejects an
unknown key, and reports the name of the key. |codeview-keymaps| lists every
action with its surface.

                                                        *codeview-backend*
The `backend` option selects the version control system. With "auto" the
plugin looks for a jj repository and for a git repository. It takes the
repository with the deepest root, so a git clone inside a jj repository keeps
the git backend. A colocated repository has a `.jj` directory and a `.git`
directory. Both roots are equal there, and the plugin takes the jj backend,
because the user drives such a repository with jj. Set the option to "git" or
to "jj" to force one backend. A forced backend needs its executable in $PATH.
Without the executable the plugin reports an error.

The jj backend reads the repository only. Every jj call runs with
`--ignore-working-copy`, so no call snapshots the working copy. A file that
you changed after the last snapshot keeps its old content in the review. For a
symbolic link the backend shows the target of the link.

A revset that names no commit gives an error that says so, for example
`trunk()..@` on a workspace with no new commit. The virtual root commit of jj
holds no files, so the backend rejects it as a revision.

15. KEYMAPS                                                   *codeview-keymaps*

Every key of codeview is buffer-local. The plugin sets no global map, and it
maps no key in a file buffer of your own. The `keymaps` option holds one entry
per action. |codeview-config| lists the defaults.

The table names the surface of each action: >

    S   the changed-files sidebar          |codeview-sidebar|
    D   the diff view, both styles         |codeview-diff|
    O   the comment overview               |codeview-overview|
    E   the comment editor                 |codeview-comments-editor|
    X   the buffer of an export            |codeview-export|
<
                                                       *codeview-keymaps-list*
>
    Action            Default        Where  What it does
    ────────────────  ─────────────  ─────  ──────────────────────────────────
    open_file         <CR>           S O    open the file, or toggle the node
                      <2-LeftMouse>  S O    a double click does the same
    toggle_node       <Tab>          S O    show or hide the children
    expand_all        zR             S O D  show every hidden line or node
    collapse_all      zM             S O D  hide every section or node
    next_file         ]f             S   D  open the next file
    prev_file         [f             S   D  open the previous file
    next_hunk         ]h                 D  jump to the next hunk
    prev_hunk         [h                 D  jump to the previous hunk
    expand_context    za                 D  show or hide the section
    load_diff         <CR>               D  render a diff above the limit *
    toggle_style      <leader>ct     S   D  switch inline and side by side
    edit_file         gf             S   D  edit the file in the working copy
    back              <leader>cb         F  back to the review from the file
    comment           <leader>cc         D  edit or write the comment
    comment_insert    i a                D  edit or write the comment
    comment_add       o O                D  write another comment on the line
    comment_visual    I A c              D  comment on the selected lines
    edit_comment      <leader>ce       O D  edit the comment
    delete_comment    <leader>cd       O D  delete the comment
    resolve_comment   <leader>cr       O D  resolve the comment, or reopen it
    show_comment      K                  D  show the comment in a float
    toggle_overview   <leader>co     S O D  open or close the overview

    editor_cancel     q  <Esc><Esc>       E  discard the comment

                                         X  close the export window
<
(*) The load key maps on a diff that the `diff.max_lines` limit stopped, and on
no other diff. `<CR>` keeps its own action in every diff that the view shows.
See |codeview-diff-limit|.

The comment editor also saves with `:w`. That write runs from an autocmd, not
from a map, so it works with any key of your own.

An entry takes one key, a list of keys, or false: >lua

    require("codeview").setup({
      keymaps = {
        show_comment = "gh",              -- one key
        comment_insert = { "i", "a" },    -- two keys for one action
        comment_visual = false,           -- no map for this action
      },
    })
<
A list of yours replaces the default list. It does not extend it.

17. HEALTH                                                     *codeview-health*

Run |:checkhealth| codeview. The report shows: >

    - the Neovim version, against the minimum version
    - the plugin version and the state of setup()
    - the result of the configuration validation
    - the git, jj, and gh executables with their versions
    - the login state of gh, from `gh auth status`
<
The login check asks GitHub whether the token is valid, so it needs a
connection. Without a login the report says how to get one.
